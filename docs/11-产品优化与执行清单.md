## 1. 结论

工程完成度 > 产品完成度。MVP 核心闭环（浏览→发点评→互动）跑通，中间件三阶段（Redis / RabbitMQ / ES）+ 管理后台 + 乐观锁均已落地。但围绕「让用户愿意第二次打开」的几块拼图缺失——本文档按 PM 优先级列出 5 项问题、落地决策与取舍，并记录本次**全部落地**的范围与延后项。

**已落地（本次）**:F1 通知 / F2 冷启动种子点评 / F3 关注 feed / F4 内容治理（举报 + 后台点评下架）/ F5 评分体感修复。
**延后（后续评估）**:敏感词过滤、审核工作流与 moderation 决策 UI、Canal binlog 增量同步、IK 中文分词、LBS 地理筛选。

> 技术纪律:沿用项目「应用层完成、infra 待办」哲学——通知走纯 MySQL + 前端轮询(不为通知加 MQ);通知写与核心互动同事务原子提交;复用 `assemble`/`PageResult.from`/`afterCommit` 既有工具,不另起锅灶。

## 3. 各项落地详情

### F1 站内通知系统(P0)

**问题**:赞了别人的点评、评论、关注,对方完全不知道,UGC 飞轮缺正反馈闭环。
**方案**:
- 新表 `t_notification`(关系式:`actor_id` 关联 `t_user`,读时批量回查昵称/头像,避免昵称改名后文案过期)。
- 三钩子点限「真正新增」后才发:点赞(`InteractionServiceImpl.like` insert 成功后)、评论(`createComment` insert 后)、关注(`FollowServiceImpl.follow` insert 后)。`actor==user` 跳过自发通知。
- **写语义取舍**:通知写与核心互动**同事务原子提交**(同库非外部 IO,非 afterCommit)——`NotificationService.create` 内部吞异常绝不阻塞核心写(沿用 `HotRankService` 吞异常约定),通知失败不影响点赞/评论/关注本体。
- 前端:顶栏铃铛 `<Badge>` + 30s 轮询未读数(`react-query refetchInterval`,全站首个轮询),`/notifications` 列表页,标记已读/全部已读后 invalidate 链上同步红点。

**取舍**:纯 MySQL、不接 MQ——通知是「非关键」正反馈,MySQL + 轮询足够;日后量大再加 Redis/MQ 属 infra 待办。未做站外推送(短信/Push),符合 MVP。

### F2 冷启动种子点评(P0)

**问题**:新克隆首屏「热门点评」空、店铺 `avgRating=0.00`/`reviewCount=0` 看似没开张。
**方案**:`data.sql` 增 3 个**不可登录**种子作者用户(沿用占位哈希约定,不固化可用口令) + ~14 条图文点评(覆盖 4 店/多城市,图片用 `picsum.photos` 外部占位图) + 少量点赞/评论;**手算对齐** `t_shop` 的 `review_count/rating_sum/avg_rating/like_count` 与 `t_user.review_count`(因 createReview 走 setSql 增量、无 recompute 方法)。
**取舍**:通知/feed 的演示用用户自注册账号互动作即可,故无需种子账号口令。图片外部 URL 需要 runtime 联网(读路径原样回放,DB 无域名约束)。

### F3 关注的人的点评(P1)

**问题**:关注后无任何地方集中看到「我关注的人最近发了什么」,关注动作对发起者无回报。
**方案**:新增 `FollowService.followeeIds`(投影查 followee_id 列)+ `ReviewService.listByFollowees`(复用私有 `assemble` 批量装 VO)+ `FeedController GET /feed/following`;前端 `/following` 页渲染 `ReviewCard`。
**取舍**:拉取式拉取(`IN(followeeIds)` + `ORDER BY create_time` 会 filesort),MVP 数据量可接受,后期可加 `idx_status_create` 优化;不上推模式/timeline(技术成本不在 MVP)。

### F4 内容治理:举报 + 后台点评下架(P1,对外前最低安全网)

**问题**:无审核/举报/下架,任何人可发任意内容,运营无法下架,对外即隐患。
**方案**:
- 举报:`t_report`(`uk_reporter_target` 限同一用户对同一目标一条,重复举报 40905 幂等),`POST /reports`(必填 targetType∈{REVIEW,COMMENT,USER,SHOP}/targetId/reason)。前端 `ReportButton` 挂在 `ReviewCard` 操作区(非本人点评、登录态)。
- 后台下架:`AdminReviewService.hideReview/restoreReview` + `/admin/reviews/{id}/hide|restore` + `/admin/reviews`(列表,含已下架)+ `/admin/reviews` 管理页。下架**镜像** `createReview` 累加与 `deleteShop` 回扣——同事务回扣 `t_shop.review_count/rating_sum`、重算 `avg_rating`、`t_user.review_count`,并 `afterCommit hotRankService.onDelete` 摘热度 ZSet;不物理删、可恢复;恢复时校验店铺仍正常(防为已下架店铺恢复点评致计数虚增)。
- 后台还有 `GET /admin/reports` 分页查阅举报线索。
**取舍 / 延后**:敏感词过滤、审核工作流、moderation 决策 UI(对举报做通过/驳回并联动下架)列为后续——本次只到「举报线索 + 后台能下架点评」。前端 `ALREADY_REPORTED(40905)` 走默认错误路径 toast,无需特殊幂等分支。

### F5 评分/点评体感修复(P2)

**问题**:`avgRating==0` 显示「0.0」空星 + 「0 点评」失真,新店/无点评被误读为「评分很低」。
**方案**:`ShopCard` 与 `ShopDetailPage` 头部:`avgRating > 0` 显示评分,否则「暂无评分」;`reviewCount == 0` 显示「暂无点评」。点评列表的 `Empty`「暂无点评,快来抢沙发」(本就正确)不动。

## 6. 验证

- 后端:`cd backend && mvn test`(76 单测全绿,Mockito 无中间件);`mvn clean package -DskipTests` 构建通过(`mvn` 需 JDK 17,默认 `JAVA_HOME` 指 8 时报 `--release` 非法)。
- 前端:`cd frontend && npm run build`(tsc -b + vite 通过,新页分块正常)、`npm run lint`(oxlint 通过)。
- 集成(可选,需 Docker):仿 `AdminShopServiceIT` 写 `NotificationIT`/`AdminReviewIT`(`@SpringBootTest` + Testcontainers MySQL),`-DRUN_IT=true`。
- 端到端:重建库(`docker compose --project-directory . -f docker/docker-compose.yml down -v && up -d --build`)→ 首页见种子点评(非空、非 0.0)→ 注册 alice/bob → bob 点赞 alice 点评 → alice 顶栏红点(≤30s)→ 点开通知、标记已读红点消失 → alice 关注 bob → `/following` 见 bob 点评 → `ReviewCard`「举报」入口 → alice 提权 `ADMIN` → `/admin/reviews` 下架某点评 → 该点评店铺详情不可见 + 评分/点评数回扣 → `ReportsList` 见举报记录。
- 种子计数自检 SQL:`SELECT shop_id, COUNT(*) ... FROM t_review GROUP BY shop_id` 与 `t_shop.review_count/rating_sum/avg_rating` 一致;`t_user.review_count` 与本人点评数一致;`t_review.like_count`/`reply_count` 与 `t_review_like`/`t_review_comment` 行数一致。
