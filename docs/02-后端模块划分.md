## 1. 后端技术栈

| 层 | 选型 | 说明 |

| 框架 | Spring Boot 3.2 + Java 17 | 主框架 |

## 4. 关键技术设计要点

### 4.1 统一返回体与全局异常
- `R<T> = {code, message, data}`，`code=0` 表示业务成功的统一约定见 `05-接口API设计.md`。
- `GlobalExceptionHandler`（`@RestControllerAdvice`）统一捕获：`MethodArgumentNotValidException`→400、`BusinessException`→业务码、`AccessDeniedException`/`AuthenticationException`→401/403、兜底 `Exception`→500；**不向前端泄露 SQL/堆栈**。
- 幂等冲突（如重复点赞）按业务成功处理，返回当前态，不抛错。

### 4.2 分页、自动填充与乐观锁
- `MybatisPlusConfig` 注册 `OptimisticLockerInnerInterceptor` + `PaginationInnerInterceptor(DbType.MYSQL)`（官方顺序：乐观锁在前、分页在后）；分页统一用 `selectPage(page, wrapper)`，回填总数，再转 `PageResult`。
- `MetaObjectHandler` 自动填充 `createTime`(INSERT)、`updateTime`(INSERT_UPDATE)；实体加 `@TableField(fill=...)`。避免 `ON UPDATE` 全字段更新时被置空。
- 乐观锁（v2 Phase B）：实体字段标 `@Version`，`updateById` 自动拼 `WHERE id=? AND version=?` 并 `SET version=?+1`；版本不符影响行数 0（**MP 不抛 `OptimisticLockingFailureException`**，Service 据 affected==0 映射为 `SHOP_VERSION_CONFLICT` 409）。`update(null, wrapper)` 类（如计数 `setSql`）entity 为空不走版本，互不影响。

### 4.3 安全（JWT 链 + 白名单 + 角色权限 + CORS）
- `SecurityConfig` 配 `SessionCreationPolicy.STATELESS`，禁用 CSRF，`addFilterBefore(JwtAuthFilter, UsernamePasswordAuthenticationFilter.class)`。
- **白名单**（`permitAll`）：注册/登录、`GET` 浏览类（shops/categories/reviews 详情与评论列表/users 主页与关注粉丝列表/home）。
- **顺序敏感**：`GET /users/me`（authenticated）必须配置在 `GET /users/**`（permitAll）之前；`/api/v1/admin/**`（hasRole('ADMIN')）必须配置在 `anyRequest().authenticated()` 之前。
- `JwtAuthFilter`：解析 `Authorization: Bearer` token，校验通过写 `SecurityContext`，失败不抛异常（交 `authenticationEntryPoint` 统一输出 401）。服务层用 `SecurityContextHelper.getCurrentUserId()` 取登录人。
- **角色**（v2 Phase B）：`t_user.role` 为 `USER`/`ADMIN`，登录写入 JWT claim；`LoginUser.getAuthorities()` 输出 `ROLE_<role>`，使 `hasRole('ADMIN')`（自动补 `ROLE_` 前缀）生效。`/api/v1/admin/**` 仅管理员可访问，普通用户 403。
- 密码 `BCryptPasswordEncoder`（strength=10）；任何 VO 不含 `password` 字段。
- CORS：`CorsConfigurationSource` 允许前端 dev/生产域名、常用方法与头、`allowCredentials=true`，经 `http.cors(withDefaults())` 启用。

### 4.4 文件存储抽象
- `FileStorageService` 接口（`service` 包）：核心方法 `upload(MultipartFile) -> {url, ossKey}`、`delete(ossKey)`。
- `OssFileStorageServiceImpl`：`@ConditionalOnProperty(prefix="storage", name="type", havingValue="oss")`，阿里云 OSS SDK，URL 由 `oss.domain + ossKey` 拼装。
- `LocalFileStorageServiceImpl`：`havingValue="local"` 且 `matchIfMissing=true`，存本地 `./data/uploads/yyyy/MM/uuid.ext`，`WebMvcConfig` 映射 `/static/uploads/**`，返回后端静态资源 URL。
- 业务层只依赖接口，不拼 URL；DB 存 `url`（可访问）+ `oss_key`（管理用）。

### 4.5 事务与幂等
- 冗余计数（点赞数/评论数/点评数/关注数/粉丝数/店铺评分汇总）在写入业务行的**同一 `@Transactional` 方法**内更新，失败整体回滚。
- 点赞：`INSERT` 撞唯一约束 `uk_review_user` 抛 `DuplicateKeyException` → 视为已点赞，返回当前计数，**不做「先查后写」**。
- 取消点赞/取关：`DELETE` 按 `affected rows` 判断，>0 才递减计数。
- 递减一律 `GREATEST(0, n-1)` 防止计数为负。
- 关注/取关复用 `uk_follower_followee` 唯一约束；不可关注自己在 Service 层校验。

### 4.6 逻辑外键与软删除
- 全部逻辑外键，不建物理 FK；关系靠 `shop_id`/`user_id`/`category_id`/`review_id` 等字段维护，Service 层校验引用存在性。
- 软删除统一用 `status`（1 正常 / 0 隐藏），不全局开启 MyBatis-Plus 逻辑删除插件；查询按需 `status=1` 过滤。

### 4.7 管理员后台模块（v2 Phase B 改店 / Phase C 删店）
- 鉴权由 `SecurityConfig` 的 `/api/v1/admin/** hasRole('ADMIN')` 统一把关，控制器不再逐方法标注。
- `AdminShopService.updateShop`：`selectById` 载入含 `version` 的店铺 → 覆盖请求体非空/null 字段（口径同 `UpdateProfileRequest`）→ `updateById` 走乐观锁；`categoryId` 非空时校验分类存在性；冲突（affected=0）→ `BusinessException(SHOP_VERSION_CONFLICT)`(409)。
- `AdminShopService.deleteShop`（Phase C）：同事务标记 `shop.status=0` + 级联 `review.status=0`（即时从公开读路径消失）+ 镜像回扣发布用户 `review_count`（`GREATEST 0` 防负）；`afterCommit` 投递延时清理消息。响应复用 `ShopService.getShopDetail`；占位 admin 账号不可登录，真实管理员走「注册后 UPDATE role='ADMIN'」提权（见 `data.sql` 注释）。

### 4.8 消息中间件——店铺删除延时清理（v2 Phase C）
- **缺省方案**：TTL + DLX，**不依赖** `rabbitmq_delayed_message_exchange` 社区插件（标准 `rabbitmq:3-management` image 即可，固定延时不踩 TTL「排序坑」）。`RabbitMQConfig` 定义：`shop.cleanup.submit`(direct 交换器) → `shop.cleanup.delay.queue`(`x-message-ttl` 充当延时窗口，`x-dead-letter-exchange→shop.cleanup.dlx`) → 过期转 `shop.cleanup.queue`(消费) → 消费失败重试耗尽经 `shop.cleanup.poison.dlx` 进 `shop.cleanup.dlq`。
- **可靠性三件套**：① publisher-confirm（`correlated`）+ returns 回调记 warn；② 消费幂等——`ShopCleanupService.cleanup` 开头 `selectById==null` 即 no-op，物理删为 `DELETE` 天然幂等，OSS/本地删图吞异常不阻断，回扣计数已在标记事务前置完成（消费端不再碰计数，避免重复递减）；③ DLQ——`spring.rabbitmq.listener.simple.retry` 内置重试，`default-requeue-rejected=false` + `shop.cleanup.queue` 的 `x-dead-letter-exchange` → DLQ 兜底毒消息。
- **at-least-once 兜底（取代独立 outbox 表）**：`ScheduledShopCleanupReconcile`(`@Scheduled`) 扫 `status=0` 且 `update_time` 超「延时+宽限」的滞留店直接调 `ShopCleanupService.cleanup`（幂等）。与 Phase A `afterCommit + ScheduledRankRebuild` 同范式；探查证仓储无 outbox 先例，故不另建表，`docs/06 §5.2.1` 的「建议 outbox」降级为本对账调度。
- **降级**：`tastelink.rabbitmq.enabled=false` 则 `ShopCleanupProducer` 不发消息，删店即时一致（标记+隐藏+回扣）不缺，物理清理由对账调度兜底（无延时窗口、稍延后）。AMQP 连接懒初始化，broker 缺席不影响应用启动。
- 删图用 `FileStorageService.ossKeyFromUrl(url)` 从可访问 URL 反推存储 key（`t_review_image.oss_key` 入库多为空串，仅 `url` 列可靠）；删店后点评经 `HotRankService.onDelete(reviewId)`（`zrem`）从全局热度 ZSet 摘除，`rebuild` 仍兜底。

### 4.9 搜索/Elasticsearch（v2 Phase D）
- **客户端**：Spring Data Elasticsearch 5.2.x（`elasticsearch-java` 8.x 新客户端，**禁用**已删的 `RestHighLevelClient`）。`ShopController.listShops` 在 `keyword` 非空时调 `SearchService.searchByKeyword`；命中结果 `List<ShopVO>` 经 `ShopService.toVOsByIds(orderedIds)` 按相关性序回填（`selectList(in id + status=NORMAL)` + `categoryNameMap` + `toShopVO`，按入参序重排，类比 `ReviewServiceImpl.hotReviews` 按 ZSet rank 重排）。
- **索引文档** `ShopDoc`(`@Document(indexName="tastelink-shop", createIndex=false)`)：仅含搜索/过滤字段 `id/name/address/description/status/categoryId/city`。**不放** `avgRating/reviewCount/categoryName`——ShopVO 组装时从 MySQL 回查，保证计数/分类名与库一致。索引名是代码常量（`@Document` 的 indexName 不支持 `${}` 占位符，故不走 yml）。
- **查询**：`ElasticsearchOperations` + `Criteria`（`name` MUST matches keyword + `status/categoryId/city` MUST 过滤）+ `PageRequest`(0-based)。**keyword 当前仅 `name` 单字段**（与 v1 `LIKE name` 等宽、严格升级为 relevance + IK-ready）；多字段（name/address/description `should + filter` 受 `minimum_should_match` 坑，需 `NativeQuery multi_match`）作小后续——`ShopDoc` 已索引这三列，扩展只改查询。
- **降级**：ES 任意异常/禁用 → `searchByKeyword` 返回 `null` → 控制器回退 `shopService.listShops`（MySQL `LIKE name`），与 Phase A/C 吞缓存/MQ 异常 + 兜底同范式。`tastelink.search.enabled=false` 直接跳过 ES。AMQP/ES/Redis 皆懒连接，无 ES 不阻塞启动。
- **索引初始化 + 对账**：`ShopIndexInitializer`(`ApplicationRunner`) 启动时若 ES 在线且索引缺失则 `createWithMapping`；`ScheduledShopReconcile`(`@Scheduled` 默认每 10 分钟) 以 MySQL `status=NORMAL` 全量 `saveAll` 灌 ES（快照式覆盖脏成员，ES 异常吞掉靠下一周期）。
- **infra 待办**：A) **IK 中文分词**——标准 `elasticsearch:8.x` image 无 IK，中文命中弱；prod 需装 `analysis-ik` + 索引 mapping 指定 `ik_max_word`/`ik_smart`（改 analyzer 需 reindex，不涉本应用层）。B) **Canal binlog 增量同步**——canal-server+canal-adapter 为独立部署进程（非应用 bean，本环境无法起 canal-server+binlog 验证，盲提交风险高），延后；本阶段以 `ScheduledShopReconcile` 全量重建兜底最终一致，Canal 落地后替换近实时、`reconcile` 退化为 drift 修正。

## 6. 代码规范约定

- 包名 `com.tastelink.<职责>`；实体与表一一对应，驼峰↔下划线自动映射。
- 请求 DTO 用 `@NotBlank/@Size/@Min/@Max` 等校验；Controller 形参加 `@Valid`。
- 响应统一封装为 `VO`，敏感字段（`password`）不出现。
- 时间字段返回统一 `yyyy-MM-dd HH:mm:ss`。
- 分页参数 `page`(从1起)/`size`，统一经分页插件，输出 `PageResult`。
- 接口实现严格遵循 `05-接口API设计.md` 的路径、参数与返回结构；契约变更需同步文档并升版本号。
