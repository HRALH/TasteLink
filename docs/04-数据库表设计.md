## 1. 设计总则

| 项 | 约定 |
|---|---|
| 存储引擎 | InnoDB |
| 字符集 | `utf8mb4` / `utf8mb4_general_ci` |
| 主键 | 统一 `id BIGINT UNSIGNED AUTO_INCREMENT`，无业务含义 |
| 时间字段 | 统一 `create_time` / `update_time`，`DATETIME`，DB 默认值兜底 + MyBatis-Plus 自动填充 |
| 外键策略 | **全部逻辑外键**，不建物理 FK 约束（便于演进、避免写放大/死锁） |
| 软删除 | 用 `status` 字段（1 正常 / 0 隐藏），不在 MyBatis-Plus 全局开启 logic-delete |
| 计数 | 点赞数/评论数/点评数/关注数/粉丝数/店铺点评数/平均评分均为**冗余字段**，写入时同事务维护 |
| 命名 | 表前缀 `t_`，字段下划线命名，MyBatis-Plus `map-underscore-to-camel-case` 自动映射 |
| 评分 | `rating TINYINT`，1~5，由 Service 层 `@Min/@Max` 校验 |

## 2. 表清单与关系

| 表 | 说明 | 主要关联（逻辑） |
|---|---|---|
| `t_user` | 用户 | — |

## 3. 表结构 DDL

### 3.1 用户表 `t_user`

```sql
CREATE TABLE `t_user` (
  `id`              BIGINT       NOT NULL AUTO_INCREMENT COMMENT '用户ID',
  `username`        VARCHAR(64)  NOT NULL                COMMENT '用户名(登录名,唯一,不可改)',
  `password`        VARCHAR(100) NOT NULL                COMMENT '密码(BCrypt哈希)',
  `nickname`        VARCHAR(64)  NOT NULL DEFAULT ''     COMMENT '昵称',
  `avatar_url`      VARCHAR(512) NOT NULL DEFAULT ''     COMMENT '头像URL',
  `bio`             VARCHAR(255) NOT NULL DEFAULT ''     COMMENT '个人简介',
  `following_count` INT          NOT NULL DEFAULT 0     COMMENT '关注数(冗余)',
  `follower_count`  INT          NOT NULL DEFAULT 0     COMMENT '粉丝数(冗余)',
  `review_count`    INT          NOT NULL DEFAULT 0     COMMENT '发布点评数(冗余)',
  `role`            VARCHAR(16)  NOT NULL DEFAULT 'USER' COMMENT '角色:USER普通/ADMIN管理员(v2 Phase B)',
  `status`          TINYINT      NOT NULL DEFAULT 1     COMMENT '状态:1正常 0禁用',
  `create_time`     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_username` (`username`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

**索引说明**
- `uk_username`：登录 `WHERE username=?` 的命中索引；唯一约束同时保证用户名不重复。

### 3.2 店铺分类字典表 `t_shop_category`

```sql
CREATE TABLE `t_shop_category` (
  `id`          BIGINT      NOT NULL AUTO_INCREMENT COMMENT '分类ID',
  `code`        VARCHAR(32) NOT NULL                COMMENT '分类编码(HOTPOT/COFFEE/BBQ/JAPANESE)',
  `name`        VARCHAR(32) NOT NULL                COMMENT '分类中文名(火锅/咖啡/烧烤/日料)',
  `sort_order`  INT         NOT NULL DEFAULT 0      COMMENT '展示排序,越小越靠前',
  `icon_url`    VARCHAR(512) NOT NULL DEFAULT ''    COMMENT '分类图标URL',
  `create_time` DATETIME   NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` DATETIME   NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_code` (`code`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='店铺分类字典表';
```

> 字典化便于统一维护名称与编码；前端用 `code` 路由更稳定，后端用 `id` 关联店铺。

### 3.3 店铺表 `t_shop`

```sql
CREATE TABLE `t_shop` (
  `id`           BIGINT       NOT NULL AUTO_INCREMENT COMMENT '店铺ID',
  `name`         VARCHAR(128) NOT NULL                COMMENT '店铺名称',
  `category_id`  BIGINT       NOT NULL                COMMENT '店铺分类ID(逻辑外键->t_shop_category.id)',
  `city`         VARCHAR(64)  NOT NULL DEFAULT ''     COMMENT '所在城市(首页按城市筛选)',
  `address`      VARCHAR(255) NOT NULL DEFAULT ''     COMMENT '详细地址',
  `longitude`    DECIMAL(10,7) NULL                  COMMENT '经度(MVP预留,不参与筛选)',
  `latitude`     DECIMAL(10,7) NULL                  COMMENT '纬度(MVP预留,不参与筛选)',
  `phone`        VARCHAR(32)  NOT NULL DEFAULT ''     COMMENT '联系电话',
  `cover_url`    VARCHAR(512) NOT NULL DEFAULT ''     COMMENT '店铺封面图URL',
  `description`  TEXT         NULL                   COMMENT '店铺简介',
  `rating_sum`   INT          NOT NULL DEFAULT 0     COMMENT '评分总和(冗余,算avg用)',
  `avg_rating`   DECIMAL(3,2) NOT NULL DEFAULT 0.00  COMMENT '平均评分(冗余,0.00-5.00)',
  `review_count` INT          NOT NULL DEFAULT 0     COMMENT '点评数(冗余,首页热度依据)',
  `like_count`   INT          NOT NULL DEFAULT 0     COMMENT '本店点评累计点赞数(冗余,热度加权用)',
  `version`      INT          NOT NULL DEFAULT 0     COMMENT '乐观锁版本号(v2 Phase B,管理员并发改店铺防覆盖)',
  `status`       TINYINT      NOT NULL DEFAULT 1     COMMENT '状态:1正常 0下架',
  `create_time`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_city_status_review`      (`city`, `status`, `review_count`),
  KEY `idx_category_status_review`  (`category_id`, `status`, `review_count`),
  KEY `idx_name`                    (`name`),
  KEY `idx_status_review_like`      (`status`, `review_count` DESC, `like_count` DESC),
  KEY `idx_status_update`           (`status`, `update_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='店铺表';
```

**索引说明**
- `idx_city_status_review`：首页/列表 `WHERE city=? AND status=1 ORDER BY review_count DESC`。
- `idx_category_status_review`：分类筛选 `WHERE category_id=? AND status=1 ORDER BY review_count DESC`。
- `idx_name`：关键字搜索 `name LIKE '%kw%'`（LIKE 前导通配无法走索引，此索引用于前缀匹配或兜底）。
- `idx_status_review_like`（B3-1）：首页/全局热榜无 city 前缀 `WHERE status=1 ORDER BY review_count DESC, like_count DESC`，消除全表扫+filesort。
- `idx_status_update`（B3-1）：删店对账扫描 `WHERE status=0 AND update_time<?`（ScheduledShopCleanupReconcile）。

> **分类单选 vs 多选**：MVP 取单选 `category_id`，便于高效联合索引且无需 JOIN 关系表。后续若需多标签，新增 `t_shop_category_relation` 多对多表，保留 `category_id` 作主分类。
> **经纬度**：MVP 不做 LBS 筛选，字段预留。

### 3.4 点评表 `t_review`

```sql
CREATE TABLE `t_review` (
  `id`          BIGINT    NOT NULL AUTO_INCREMENT COMMENT '点评ID',
  `shop_id`     BIGINT    NOT NULL                COMMENT '所属店铺ID(逻辑外键->t_shop.id)',
  `user_id`     BIGINT    NOT NULL                COMMENT '发布用户ID(逻辑外键->t_user.id)',
  `city`        VARCHAR(64) NOT NULL DEFAULT ''   COMMENT '冗余店铺城市(首页按城市精选点评,避免JOIN)',
  `content`     TEXT      NOT NULL                COMMENT '点评文字内容',
  `rating`      TINYINT   NOT NULL                COMMENT '评分1-5',
  `like_count`  INT       NOT NULL DEFAULT 0     COMMENT '点赞数(冗余)',
  `reply_count` INT       NOT NULL DEFAULT 0     COMMENT '评论数(冗余)',
  `status`      TINYINT   NOT NULL DEFAULT 1     COMMENT '状态:1正常 0隐藏',
  `create_time` DATETIME  NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` DATETIME  NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_shop_status_create` (`shop_id`, `status`, `create_time`),
  KEY `idx_user_status_create` (`user_id`, `status`, `create_time`),
  KEY `idx_status_like`        (`status`, `like_count`),
  KEY `idx_city_like`          (`city`, `status`, `like_count`),
  KEY `idx_shop_status_like`   (`shop_id`, `status`, `like_count` DESC)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='点评表';
```

**索引说明**
- `idx_shop_status_create`：店铺下点评列表 `WHERE shop_id=? AND status=1 ORDER BY create_time DESC`，索引末列 `create_time` 利用有序性避免 filesort。
- `idx_user_status_create`：用户主页的点评列表。
- `idx_status_like`：首页「热门点评」，全局 `WHERE status=1 ORDER BY like_count DESC`。
- `idx_city_like`：首页「热门点评」按城市 `WHERE city=? AND status=1 ORDER BY like_count DESC`，依赖冗余 `city` 字段免 JOIN。
- `idx_shop_status_like`（B3-1）：店铺点评按热度排序 `WHERE shop_id=? AND status=1 ORDER BY like_count DESC`（`sortBy=like`）。

### 3.5 点评图片表 `t_review_image`

```sql
CREATE TABLE `t_review_image` (
  `id`          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '自增ID',
  `review_id`   BIGINT       NOT NULL                COMMENT '点评ID(逻辑外键->t_review.id)',
  `url`         VARCHAR(512) NOT NULL                COMMENT '图片可访问URL',
  `oss_key`     VARCHAR(512) NOT NULL DEFAULT ''    COMMENT 'OSS对象key(删除时清理存储用)',
  `sort_order`  INT          NOT NULL DEFAULT 0      COMMENT '展示排序',
  `create_time` DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_review_sort` (`review_id`, `sort_order`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='点评图片表';
```

> **一对多关系表 vs 单表多列 `image_url_1..9`**：取一对多关系表。原因：符合 1NF；支持任意数量与排序；按 `review_id IN (...)` 批量取图后内存分组，避免 N+1。

### 3.6 点评点赞表 `t_review_like`

```sql
CREATE TABLE `t_review_like` (
  `id`         BIGINT   NOT NULL AUTO_INCREMENT COMMENT '自增ID',
  `review_id`  BIGINT   NOT NULL                COMMENT '被点赞的点评ID',
  `user_id`    BIGINT   NOT NULL                COMMENT '点赞用户ID',
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_review_user` (`review_id`, `user_id`),
  KEY `idx_user_create` (`user_id`, `create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='点评点赞表(MVP仅点评可点赞)';
```

**索引说明**
- `uk_review_user`：幂等核心。并发场景下，唯一约束是「同一用户对同一点评只能有一条」的最终兜底，配合 `DuplicateKeyException` 判定已点赞。
- `idx_user_create`：可选，「我点赞过的点评」列表查询。
- `review_id` 作为联合唯一索引前缀，也覆盖「某点评被谁点赞」查询。

### 3.7 点评评论表 `t_review_comment`

```sql
CREATE TABLE `t_review_comment` (
  `id`          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '评论ID',
  `review_id`   BIGINT       NOT NULL                COMMENT '所属点评ID(逻辑外键->t_review.id)',
  `user_id`     BIGINT       NOT NULL                COMMENT '评论用户ID',
  `content`     VARCHAR(500) NOT NULL                COMMENT '评论内容',
  `status`      TINYINT      NOT NULL DEFAULT 1     COMMENT '状态:1正常 0隐藏',
  `create_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
```

> 单层结构：无 `parent_id`、无楼中楼。分页 `WHERE review_id=? AND status=1 ORDER BY create_time` 走 `idx_review_status_create`。

### 3.8 关注关系表 `t_follow`

```sql
CREATE TABLE `t_follow` (
  `id`          BIGINT   NOT NULL AUTO_INCREMENT,
  `follower_id` BIGINT   NOT NULL                COMMENT '关注者(发起关注的用户ID)',
  `followee_id` BIGINT   NOT NULL                COMMENT '被关注者(被关注的用户ID)',
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_follower_followee` (`follower_id`, `followee_id`),
  KEY `idx_follower_create` (`follower_id`, `create_time`),
  KEY `idx_followee_create`  (`followee_id`, `create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户关注关系表';
```

**关注列表 vs 粉丝列表（双向查询）**
- 关注列表（A 关注了谁）：`WHERE follower_id=A ORDER BY create_time DESC` → 走 `idx_follower_create`，等值+有序，无需 filesort。
- 粉丝列表（谁关注了 A）：`WHERE followee_id=A ORDER BY create_time DESC` → 走 `idx_followee_create`，等值+有序，无需 filesort。
- `uk_follower_followee` 兼任「重复关注」防御与「取消关注」`WHERE follower_id=? AND followee_id=?` 的命中索引。

> 深分页 `LIMIT 100000,20` 在关注量巨大时仍慢，MVP 数据量小可接受；未来可改游标分页（`WHERE create_time < ? ORDER BY create_time DESC LIMIT N`）。

### 3.9 站内通知表 `t_notification`（产品优化 F1）

```sql
CREATE TABLE IF NOT EXISTS `t_notification` (
  `id`           BIGINT       NOT NULL AUTO_INCREMENT COMMENT '通知ID',
  `user_id`      BIGINT       NOT NULL                COMMENT '接收者(被互动方)',
  `actor_id`     BIGINT       NOT NULL                COMMENT '触发者(点赞/评论/关注的人)',
  `type`         VARCHAR(32)  NOT NULL                COMMENT '类型:REVIEW_LIKED/REVIEW_COMMENTED/USER_FOLLOWED',
  `target_type`  VARCHAR(16)  NOT NULL                COMMENT '目标:REVIEW/USER',
  `target_id`    BIGINT       NOT NULL                COMMENT '目标ID',
  `preview`      VARCHAR(255) NOT NULL DEFAULT ''     COMMENT '快照摘要(如评论内容片段)',
  `is_read`      TINYINT      NOT NULL DEFAULT 0     COMMENT '0未读 1已读',
  `create_time`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_user_read_create` (`user_id`, `is_read`, `create_time` DESC)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='站内通知表';
```

**设计取舍**：**关系式而非快照**——`actor_id` 关联 `t_user`，读时批量回查昵称/头像（与 `ReviewServiceImpl.assemble` 同手法），避免用户改名后通知文案过期。`idx_user_read_create` 单索引同时撑「我的通知分页(时间倒序)」与「未读数 `WHERE user_id=? AND is_read=0`」。
**写语义**：被赞/被评/被关注瞬间写一条；`actor==user`（自己互动自己）跳过；通知写与核心互动**同事务原子提交**（同库非外部 IO），`NotificationService.create` 内部吞异常绝不阻塞核心写。

### 3.10 内容举报表 `t_report`（产品优化 F4）

```sql
CREATE TABLE IF NOT EXISTS `t_report` (
  `id`          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '举报ID',
  `reporter_id` BIGINT       NOT NULL                COMMENT '举报人(登录用户)',
  `target_type` VARCHAR(16)  NOT NULL                COMMENT '目标:REVIEW/COMMENT/USER/SHOP',
  `target_id`   BIGINT       NOT NULL                COMMENT '目标ID',
  `reason`      VARCHAR(255) NOT NULL                COMMENT '举报理由(枚举文案 KEY)',
  `status`      VARCHAR(16)  NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING 待处理 / RESOLVED 已处理',
  `create_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_reporter_target` (`reporter_id`, `target_type`, `target_id`),
  KEY `idx_status_create` (`status`, `create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='内容举报表';
```

**幂等**：`uk_reporter_target` 限同一用户对同一目标只记一条，重复举报 `INSERT` 撞唯一键 → 抛 `ALREADY_REPORTED(40905)`，前端默认错误路径 toast「已举报过该内容」。`idx_status_create` 供后台按状态+时间分页查阅。
**定位**：对外前最低安全网，仅做「举报线索 + 后台下架点评」；敏感词过滤、审核工作流、moderation 决策 UI 列为后续。

## 4. 关键冗余计数字段维护说明

| 计数字段 | 所属表 | +1 触发 | -1 触发 | 实现 |
|---|---|---|---|---|
| `like_count` | t_review | 点赞成功（新增 like 行） | 取消点赞成功（删除 like 行>0） | `UPDATE SET like_count=like_count±1`，减时用 `GREATEST(0,like_count-1)` 防负 |
| `reply_count` | t_review | 评论成功（新增评论） | 删评论（status=0） | 同上 |
| `review_count` | t_shop | 新增点评 | 删点评（status=0） | 同上，减时 GREATEST 防负 |
| `rating_sum` / `avg_rating` | t_shop | 新增点评 `rating_sum+=rating`，`avg_rating=round(rating_sum/review_count,2)` | 删点评：`rating_sum-=rating` 并重算 `avg_rating` | 同事务维护 |
| `like_count` | t_shop | 点评被点赞时累加（可选热度加权） | 取消点赞递减 | 可选，用于店铺热度 |
| `following_count` | t_user | 关注成功 | 取消关注成功 | 减时 GREATEST 防负 |
| `follower_count` | t_user | 被关注成功 | 被取消关注成功 | 同上 |
| `review_count` | t_user | 用户新增点评 | 用户删点评 | 同上 |

**事务边界**：插入/删除业务行 与 对应计数 UPDATE 必须在**同一个 `@Transactional` 方法**内，任一失败整体回滚。

> **v2 Phase C 删店口径补充**：管理员删店（`AdminShopService.deleteShop`）走「两段式」——标记事务内把 `t_shop.status=0` 与该店 `t_review.status=0` 同事务置位，并**前置**镜像回扣发布用户 `t_user.review_count`（按被标点评数聚合累减，`GREATEST 0` 防负，保即时一致）。**B2-2 起同步回扣店铺计数**：按被隐藏点评聚合 `SUM(rating)/COUNT(*)`，置 `review_count = GREATEST(0, review_count - n)`、`rating_sum = GREATEST(0, rating_sum - sum)` 并重算 `avg_rating = IF(review_count=0, 0, ROUND(rating_sum/review_count, 2))`——否则店铺恢复（status 回 1）后评分/点评数永久虚高。物理级联删 `t_review_image→t_review_like→t_review_comment→t_review→t_shop` 不再触计数，依赖上述前置回扣；重复投递安全（DELETE 天然幂等 + `selectById==null` no-op）。
>
> **`t_review_image.oss_key` 口径**：B1-1 起 `createReview` 入库时由 `FileStorageService.ossKeyFromUrl(url)` 反推真实写入该列（入参仅 url，OSS 形态为 `uploads/yyyy/MM/uuid.ext`，Local 形态为 `yyyy/MM/uuid.ext`）；删店清图直接用列值，历史空串行回退 URL 反推（Local 去 `publicBaseUrl+urlPrefix/` 前缀；OSS 去 `domain/` 或 `https://{bucket}.{endpoint}/` 前缀）。

**幂等实现要点**
- 点赞：`INSERT` 撞 `uk_review_user` 抛 `DuplicateKeyException` → 视为已点赞，返回当前计数，不做计数变更；不用「先 SELECT 后 INSERT」。
- 取消点赞：`DELETE WHERE review_id=? AND user_id=?`，按 `affected rows` 判断，>0 才减计数。
- 关注/取关：同上（唯一约束 `uk_follower_followee`）。
- 举报：`INSERT` 撞 `uk_reporter_target` 抛 `DuplicateKeyException` → 转抛 `ALREADY_REPORTED(40905)`，前端 toast「已举报过该内容」。

> **管理员点评下架/恢复口径（F4 `AdminReviewService`）**：镜像 `createReview` 累加与 `AdminShopService.deleteShop` 回扣——下架（`review.status=0`）同事务 `t_shop.review_count/rating_sum` 递减（`GREATEST 0` 防负）、重算 `avg_rating=IF(review_count=0,0,ROUND(...))`、`t_user.review_count` 递减，并 `afterCommit` 调 `hotRankService.onDelete(reviewId)` 摘热度 ZSet；恢复（`review.status=1`）反向加回（且校验店铺仍 status=1，避免为已下架店铺恢复点评致计数虚增）。不物理删，可恢复。
