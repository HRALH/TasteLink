## 0. 全流程与三条铁律

```
本地改代码 → 本地自检 → commit + push → CI 绿 → 服务器 git pull → 只重建改动的部分 → 验收
                                                                          ↓ 不对
                                                                       回滚（重建旧镜像）
```

**三条铁律**（违反其中任何一条，代价都不对称地大）：

1. **只在本地改代码，服务器上只做 `pull` 和重建。** 在服务器上直接改文件能立刻生效，但那次改动不在 git 里：下次 `pull` 会冲突，出问题无法回滚，换台机器部署不出来。（唯一的例外：`docs/14 §4` 的端口加固，见 §9。）
2. **改数据库结构之前必须先备份。** 项目**没有 Flyway/Liquibase**，DDL 是唯一一个"代码回滚不等于状态回滚"的动作，见 §6。
3. **不要用 `tlc down -v`**，除非你明确要"回到全新状态"——它会连数据库和已上传的图片一起删。

## 1. 本地自检（push 之前必做）

CI 是第二道防线，不是第一道。本地能跑通再推，省下一轮"推上去发现红的、改一下再推"的往返。

```bash
# 后端：纯 Mockito 单测，不需要 DB/Redis/MQ
cd backend && mvn test

# 前端：类型检查 + lint + 组件测试 + 构建（build 会跑 tsc，能提前抓出类型错误）
cd frontend && npm run lint && npm run test:run && npm run build
```

需要真实中间件的集成测试（`-DRUN_IT=true`，Testcontainers）本地按需跑，CI 里**不跑**：

```bash
cd backend
mvn test -DRUN_IT=true -Dtest=HotRankServiceIT      # 真 Redis
mvn test -DRUN_IT=true -Dtest=AdminShopServiceIT    # 真 MySQL
mvn test -DRUN_IT=true -Dtest=ShopCleanupIT         # 真 RabbitMQ
mvn test -DRUN_IT=true -Dtest=SearchServiceIT       # 真 ES
```

> 改动了中间件相关逻辑（热榜 / 删店清理 / ES 检索）时建议本地跑一次对应的 IT，这类问题单测覆盖不到，而且线上症状很轻（自动降级到 MySQL，功能看着正常）。

## 2. 提交与 CI 门禁

```bash
git add -A
git commit -m "feat(scope): 说明"      # 与仓库既有风格一致：feat/fix/docs(scope): 中文说明
git push
```

CI 触发条件（`.github/workflows/ci.yml`）：

| 事件 | 范围 |
|---|---|
| `push` | `main`、`feature/**` |
| `pull_request` | 目标为 `main` |

CI 跑什么：

| Job | 内容 |
|---|---|
| `backend` | JDK 17（temurin）+ `mvn -B -ntp test` |
| `frontend` | Node **24** + `npm ci` + `lint` + `test:run` + `build` |

> 前端 job 的 Node 版本**必须是 24**（或 ≥22.19）：`jsdom → undici 8` 要求 `node >= 22.19.0`，跑在 Node 20 上会缺 `webidl.util.markAsUncloneable`，vitest 的 forks worker 全部起不来。这条已经踩过一次，别改回去。

**CI 绿了再动服务器。**

## 3. 服务器更新

### 3.1 标准四步

```bash
cd /opt/TasteLink

# 1) 先看有没有本地改动（正常情况下只有 docker/docker-compose.yml，见 §9）
git status --short
git stash              # 有改动才需要，见 §9

# 2) 拉代码
git pull

# 3) 按改动范围重建（见 3.2 对照表）
tlc up -d --build backend

# 4) 验收（见 §8）
tlc ps
curl -s http://127.0.0.1:8080/actuator/health; echo
```

### 3.2 改动类型 → 重建范围

| 改了哪里 | 命令 | 大致耗时 / 影响 |
|---|---|---|
| `backend/**`（Java 代码、`application.yml`、mapper XML、`db/*.sql`） | `tlc up -d --build backend` | 1~3 分钟；接口中断十几秒到一分钟（容器重建 + Spring 启动） |
| `frontend/**`（React/TS/CSS） | `tlc up -d --build frontend` | 30~90 秒；期间页面 502 |
| 两边都改 | `tlc up -d --build` | 只重建有变化的层 |
| 只改根目录 `.env`（如 `CORS_ORIGINS`） | `tlc up -d` | 秒级；**不重建镜像**，只重建容器让新环境变量生效 |
| `docker/docker-compose.yml`（端口 / 挂载 / 环境变量映射） | `tlc up -d` | 秒级；compose 只重建"配置变了"的容器 |
| `docker/nginx.conf`（前端容器内 nginx 配置） | `tlc up -d --build frontend` | 1 分钟内；nginx.conf 是**构建期** `COPY` 进镜像的，`up -d` 单独跑不会生效 |
| `docker/Dockerfile.*` | 对应服务 `tlc up -d --build <service>` | 同该服务 |
| `docs/**`、`CLAUDE.md` | 不用任何操作 | 纯文档，`git pull` 即可 |

### 3.3 为什么日常更新比首次构建快得多

Docker 按层缓存，而依赖层只由清单文件决定：

- 后端第一步是 `COPY backend/pom.xml` + `mvn dependency:go-offline`。**只要 `pom.xml` 没变，这一层直接复用**，不会重下 Maven 依赖；随后 `COPY backend/src` 变化 → 只重跑 `mvn clean package -DskipTests`（编译 + 打包）。
- 前端第一步是 `COPY frontend/package.json frontend/package-lock.json` + `npm ci`。**只要 lock 文件没变，这一层直接复用**；只有 `npm run build` 重跑。

所以：**只改业务代码 = 分钟级；动了 `pom.xml` 或 `package-lock.json` = 回到首次构建那种量级**（要重下依赖，见 `docs/14 §5.3` 的网络说明）。

## 4. 配置类变更（不动代码）

### 4.1 `.env`（在仓库根，被 gitignore，`git pull` 不会碰它）

改完必须让容器拿到新值：

```bash
tlc up -d <service>     # 例如 tlc up -d backend；不带 --build
```

改完**先自检再重启**，避免打错字导致服务起不来：

```bash
tlc config --environment | awk -F'= ' '{print $1" = "(length($2) > 12 ? length($2)" chars" : $2)}'
```

当前 `.env` 里每一项的含义见 `docs/08 §6 环境变量总表`。其中两个容易忘：

- `STORAGE_PUBLIC_BASE_URL`：**改域名必须同时修库里的旧图片 URL**，否则老图片全坏链（`docs/14 §8.3` 有修复 SQL）。
- `CORS_ORIGINS`：走同源反代时理论上不触发 CORS，但换域名后建议同步更新兜底。

### 4.2 `docker/docker-compose.yml`

compose 只重建"解析后配置有变化"的容器，所以改端口/挂载后：

```bash
tlc up -d                     # 一般就够
tlc up -d --force-recreate    # 没反应时强制重建
```

### 4.3 `docker/nginx.conf`

构建期 `COPY` 进前端镜像，必须 `--build`：

```bash
tlc up -d --build frontend
```

## 5. 数据安全边界

| 动作 | 数据库（`tastelink_mysql_data`） | 上传图片（`tastelink_backend_uploads`） |
|---|---|---|
| `tlc up -d --build` / `tlc build` | 安全 | 安全 |
| `tlc restart <service>` | 安全 | 安全 |
| `tlc down`（**不带 `-v`**） | 安全 | 安全 |
| 服务器 `reboot` | 安全 | 安全 |
| `tlc down -v` | **删除** | **删除** |

> 两个卷可以用 `docker volume ls` 确认。镜像是无状态的，**改代码永远不会碰数据**——这是"重建镜像"敢于随手执行的根本原因。

## 6. 数据库结构变更（本项目最需要小心的一环）

**现状**：项目**没有 Flyway / Liquibase**（`backend/pom.xml` 里没有），`spring.sql.init.mode=never`，`schema.sql` / `data.sql` 只在 `mysql_data` 卷为空时由 MySQL 容器的 `docker-entrypoint-initdb.d` 执行一次（`docs/14 §5.2`）。

**因此：改了 `schema.sql` 不会自动生效。** 正确做法是**两处都改**：

```bash
DBP=$(grep '^DB_PASSWORD=' /opt/TasteLink/.env | cut -d= -f2-)

# 1) 手工对线上库执行 DDL
docker exec tastelink-mysql mysql --default-character-set=utf8mb4 -uroot -p"$DBP" tastelink \
  -e "ALTER TABLE t_review ADD COLUMN xxx VARCHAR(32) DEFAULT NULL COMMENT '说明';"

# 2) 确认生效
docker exec tastelink-mysql mysql --default-character-set=utf8mb4 -uroot -p"$DBP" tastelink \
  -e "SHOW COLUMNS FROM t_review LIKE 'xxx';"
```

同时把同样的 DDL 写进 `backend/src/main/resources/db/schema.sql`，让**以后从零部署**得到一致的表结构（否则新机器建出来的库缺这一列，代码一跑就报错）。

**顺序很重要**：备份 → 改库 → 改代码 → 发布。

### 6.1 新增独立库的情形：`xxl_job`（B5 起）

调度中心的库**不在** `schema.sql` 里，是独立的一份：`docker/xxl-job/tables_xxl_job.sql`，挂为 MySQL 容器的 `03-` 初始化脚本。它同样**只在数据卷为空时执行**，所以：

- **全新部署**（`docs/14` 流程）：什么都不用做，`xxl_job` 库会被自动创建；起 admin 用 `docker compose ... --profile xxl-job up -d`。
- **已有部署**（`docs/15` 流程，数据卷非空）：容器重建**不会**补建这个库，而 `docker/docker-compose.yml` 里的 admin 服务此时起来会因连不上库而反复重启。两种处理：

```bash
# ① 暂不需要调度中心：什么都不做。admin 带 profiles: ["xxl-job"]，默认 up -d 不会起它，
#    后端 XXL_JOB_ENABLED 默认 false，业务与定时任务与升级前完全一致 —— 这是默认路径。
# ② 需要调度中心：手动导入库，再起 admin
DBP=$(grep '^DB_PASSWORD=' /opt/TasteLink/.env | cut -d= -f2-)
docker compose --project-directory . -f docker/docker-compose.yml \
  exec -T mysql mysql -uroot -p"$DBP" < docker/xxl-job/tables_xxl_job.sql
# 校验
docker compose --project-directory . -f docker/docker-compose.yml \
  exec -T mysql mysql -uroot -p"$DBP" -e "SELECT COUNT(*) FROM xxl_job.xxl_job_info;"
```

> **不要**为了补这个库去 `down -v`——那会连业务库和图片一起删（§5）。`xxl_job` 只有调度配置，丢了重建即可；业务库不是。
>
> 反向注意：把 `XXL_JOB_ENABLED` 置 `true` 之前**必须**确认 admin 已就绪。开关为 true 而 admin 不可达时，本地 cron 已让位，三个对账任务会静默停摆（admin 侧看不到、应用侧只有 executor 注册失败的 warn）。这也是它默认 `false` 的原因。

```bash
# 备份（脚本见 docs/14 §9.2）
mysqldump --single-transaction ... tastelink > /opt/backup/tastelink-$(date +%F).sql
```

> 加字段一般是向后兼容的，可以"先改库再发代码"。但**删列 / 改类型 / 改唯一约束**属于破坏性变更，务必先备份再动，并且要确认没有旧版本的代码还在依赖它。

## 7. 回滚

```bash
cd /opt/TasteLink
git log --oneline -5
git checkout <上一个好的提交>      # 分离头指针状态，只是临时用
tlc up -d --build                  # 按旧代码重建镜像
# 或只回滚一个服务：tlc up -d --build backend

# 修好之后回到主分支
git checkout main
git pull
```

回滚的边界（**必须清楚**）：

- **代码可以秒级回滚**，数据不会因为回滚而丢失。
- **数据库结构不会跟着回滚。** 如果坏掉的那个提交执行过 DDL，你回滚的代码要能在**已经改过的库结构**上跑；否则就要写逆向 DDL，那之前必须靠备份。
- **上传的图片不会回滚**，也不需要。

## 8. 更新后验收

### 8.1 确认新版本真的生效（最容易漏的一步）

"我重建了"不等于"新代码在跑"。四种确认方式，按可靠性排序：

```bash
# 1) 镜像 / 容器的创建时间是不是刚刚
docker images --format '{{.Repository}}:{{.Tag}}  {{.CreatedAt}}' | grep tastelink
docker ps --format '{{.Names}}  {{.Created}}'

# 2) 后端：看启动日志的时间戳 + 有没有报错
tlc logs --tail=30 backend

# 3) 前端：看 index.html 引用的 JS 文件名哈希变了没（Vite 产物带内容哈希）
curl -s http://127.0.0.1:8081/ | grep -o 'assets/[^"]*\.js'

# 4) 数据库结构变更：直接查列是否存在
docker exec tastelink-mysql mysql --default-character-set=utf8mb4 -uroot -p"$DBP" tastelink \
  -e "SHOW COLUMNS FROM t_review LIKE 'xxx';"
```

浏览器一定要 **`Ctrl-F5` 强刷**（或开无痕窗口）：前端静态资源带哈希文件名，但 `index.html` 本身可能被缓存，导致页面还在跑旧的 JS。

### 8.2 冒烟清单

| 检查 | 命令 / 操作 | 通过标准 |
|---|---|---|
| 容器 | `tlc ps` | 6 个都 `Up`，`mysql` 为 `(healthy)` |
| 后端 | `curl -s http://127.0.0.1:8080/actuator/health; echo` | `{"status":"UP"}` |
| 前端 | 浏览器开 `http://<公网IP>:8081` | 页面正常、无控制台报错 |
| 公开接口 | `curl -s http://127.0.0.1:8080/api/v1/home \| head -c 200` | `code:0` + 有数据 |
| 中文不乱码 | 任一列表页 | 中文正常（防字符集回归） |
| 登录态 | 登录后点一次关键写操作 | 成功，计数/列表随之变化 |
| 中间件未降级 | `tlc logs backend \| grep -iE "redis\|amqp\|elastic\|降级" \| tail` | **无新增 warn**（有空输出最好） |

> 改动涉及点赞 / 删店 / 检索时，额外按 `docs/14 §7.3` 验「中间件是否真的在生效」——中间件挂了会自动降级到 MySQL，功能看着正常，是最容易悄悄出问题的地方。

## 9. 服务器上的本地改动与 git 冲突（当前唯一的摩擦点）

`docs/14 §4` 让服务器对 `docker/docker-compose.yml` 做了一次**仓库里没有的**手改（把 3306/6379/5672/15672/9200/8080 从 `0.0.0.0` 收成 `127.0.0.1`）。于是：

```bash
git status --short
#  M docker/docker-compose.yml      ← 这一行应该永远只有它
```

**拉代码时按情况处理**：

| 情况 | 做法 |
|---|---|
| 仓库这次没动 `docker-compose.yml` | 直接 `git pull` 即可，git 会合并（其实无冲突面） |
| 仓库这次动了 `docker-compose.yml` | `git stash` → `git pull` → `git stash pop`；若 `pop` 报冲突，手工解决后**重新打一遍端口加固**（下面是那 5 条 sed） |

```bash
# 端口加固（§4）：stash/checkout 之后需要重新打
sed -i \
 -e 's|ports: \["3306:3306"\]|ports: ["127.0.0.1:3306:3306"]|' \
 -e 's|ports: \["6379:6379"\]|ports: ["127.0.0.1:6379:6379"]|' \
 -e 's|ports: \["5672:5672", "15672:15672"\]|ports: ["127.0.0.1:5672:5672", "127.0.0.1:15672:15672"]|' \
 -e 's|ports: \["9200:9200"\]|ports: ["127.0.0.1:9200:9200"]|' \
 -e 's|ports: \["8080:8080"\]|ports: ["127.0.0.1:8080:8080"]|' \
 docker/docker-compose.yml
grep -n 'ports:' docker/docker-compose.yml     # 应 6 行，最后一行 8081:80 不动
```

> **想根治**：把端口加固作为仓库默认值提交（改 5 行 + 同步 `docs/14 §4`），此后服务器 `git status` 永远干净、`git pull` 永不冲突，新机器 clone 下来也默认是收紧的。唯一代价：本地开发时若要从**别的机器**连本机 MySQL，需临时改回 `0.0.0.0`（同机访问不受影响）。

## 10. 排错速查（更新场景）

| 现象 | 原因 / 处置 |
|---|---|
| `git pull` 报 `Your local changes would be overwritten` | 见 §9：`git stash` 后再 pull；**不要用 `git checkout .`**，那会把端口加固一起冲掉 |
| `--build` 了几分钟就结束，改动没生效 | 改动在没被 `COPY` 的路径里，或改的是构建期配置（如 `nginx.conf`）。对照 §3.2 表；用 §8.1 确认镜像/容器时间 |
| 前端改了但页面还是老的 | 浏览器缓存 `index.html`：`Ctrl-F5` / 无痕窗口；再确认 `curl / \| grep assets/` 的哈希变了 |
| 走了 `up -d` 但环境变量没生效 | 环境变量只在**容器重建**时注入。`tlc up -d <service>`；仍无效再 `--force-recreate` |
| 后端容器起来又反复重启 | `tlc logs --tail=100 backend`。常见：DDL 没执行（§6）、`.env` 打错字（§4.1）、改了 `pom.xml` 但本地没测 |
| `Killed`（构建中 mvn/npm 被杀） | OOM：先 `tlc down` 释放内存再重建（`docs/14 §11`） |
| 更新后中文变乱码 | 字符集回归：确认两个 SQL 开头的 `SET NAMES utf8mb4;` 还在（`docs/14 §5.2`） |
| 更新后上传图片报权限错误 | `/app/data/uploads` 属主被改回 root：确认 `Dockerfile.backend` 里 `mkdir -p /app/data/uploads` + `chown` 还在（`docs/14 §5.3`） |
| 想彻底重来 | 备份 → `tlc down -v` → `tlc up -d --build` → 从备份恢复。**先备份**（§6） |
