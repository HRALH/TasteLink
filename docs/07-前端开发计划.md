## 0. 背景与原则

本计划是 `docs/06` 后端中间件升级的**前端配套**。后端 Phase A（点评审排行）纯后端、前端零改动，故本计划只覆盖 **B / C / D** 三块对应的前端工作 + 贯穿前端的公共前置（FE-0）。

> 核心事实：当前前端**完全没有管理员界面**，也**没有配置测试 runner**（见 `CLAUDE.md`、`docs/03`）。B/C 会带来全新建的管理后台前端面，D 会改写公共搜索读路径。这是开此计划的两条主轴。

### 0.1 总体原则（贯穿前端）

1. **后端先行、契约对齐**：前端每个阶段都有"后端依赖"前置项；后端契约到位前不落前端实现，避免对着假接口写。
2. **视觉系统不可破**：所有新建 admin / search UI 必须取自 `src/styles/tokens.ts` + `index.css :root`，复用 `src/components/editorial/*`，**禁止散落 hex、禁止回退 AntD 默认橘色**（admin 后台尤易回退默认样式，需重点把关）。
3. **接口签名优先不变**：能用现有 `/api/v1/shops?keyword=` 满足的就不新增端点，降低前端改动面。
4. **错误码可编程化**：B 的"乐观锁冲突"需要前端弹窗而非通用 toast，这要求 `request.ts` 拦截器能把错误码透传给调用方（FE-0 解决，承重改动）。
5. **先补测试基线**：前端当前无测试 runner；与后端 Phase 0 投 Testcontainers 对齐，引入 vitest + RTL + msw，再逐步补。

## 1. 与后端计划的对应关系

| 前端阶段 | 对应后端阶段 | 前端工作 | 后端依赖（必须先就位） |
|---|---|---|---|
| FE-0 | Phase 0 | 公共前置：角色字段 / Admin 守卫 / 拦截器透传错误码 / 类型补充 / 测试基线 | 后端 `ResultCode` 新增 `SHOP_VERSION_CONFLICT`；`/auth/login`、`/users/me` 响应含 `role` |
| FE-A | 合并 A | **无前端改动**（后端缓存对前端透明，`GET /home` 返回结构不变） | — |
| FE-B | Phase B | 管理员改店铺页 + 角色 gating + 乐观锁冲突弹窗 | 后端 B3 角色鉴权上线；`PUT /api/v1/admin/shops/{id}` 就绪 |
| FE-C | Phase C | 管理后台内的店铺删除动作 + 安全二次确认 + 下架/清理中状态 | 后端 `DELETE /api/v1/admin/shops/{id}` 就绪；admin 列表能返回 `status`（区分软删/物理删） |

> **顺序结论**：FE-0 → FE-B → FE-C → FE-D。FE-B/C 可共享同一套"管理后台"前端面，建议连续开发。

## 2. FE-0 —— 公共前置（前端地基，先于 B/C/D 完成）

### 2.1 目标
让前端具备"识别管理员"、"按错误码做分支处理"、"承载新契约类型"三个基础能力，并补测试 runner。

### 2.2 开发步骤
- [ ] **F01 `types/api.ts` 增字段**：`UserInfo`/`UserVO` 增 `role?: 'USER' | 'ADMIN'`；新增 `UpdateShopRequest`、`AdminShopVO`（含 `status` / `version`）、搜索结果类型（若 D 新增端点）。
- [ ] **F02 `authStore` 承载角色**：`src/store/authStore.ts` 的 `userInfo` 增加 `role`；登录时由 `/auth/login` 响应写入；新增 `isAdmin` 派生选择器（`role === 'ADMIN'`），持久化到 `localStorage`（key `tastelink-auth`）。
- [ ] **F03 错误码常量**：`src/utils/constants.ts` 的 `Code` 增 `SHOP_VERSION_CONFLICT: 409`（与后端 `ResultCode` 对齐，遵守 CLAUDE.md「码值两端对齐」约定）。
- [ ] **F04 拦截器透传错误码（承重）**：改 `src/api/request.ts` 响应拦截器——对于 `code≠0` 的非幂等分支，reject 一个带 `code`（及可选 `data`）的 `ApiError`；并引入 `PROCESSABLE_CODES = [Code.SHOP_VERSION_CONFLICT]`，命中时**抑制自动 `message.error`**（交给调用方弹窗），其余行为保持不变。不破坏现有 idempotent（40902/40903 当成功）与 401 跳登录逻辑。
- [ ] **F05 管理员路由守卫**：`src/router/index.tsx` 新增 `RequireAdmin`（`isLoggedIn && isAdmin`，否则重定向 `/` 或 404），后续 admin 路由复用。
- [ ] **F06 视觉占位**：在 `src/components/editorial/` 预备可能复用件（如 `Highlight` 高亮组件留到 FE-D；admin 卡片复用现有 `ShopCard`/`UserCard` 风格）。
- [ ] **F07 测试基线**：`frontend/` 引入 `vitest` + `@testing-library/react` + `msw`；`package.json` 加 `test` 脚本；示例一个 mock `/shops` 的列表测试跑通，作为后续每阶段补测的样板。
- [ ] **F08 文档**：`docs/03` 增补"角色与错误码透传"小节、预告 admin 模块；`CLAUDE.md` 前端架构段补 `ApiError`/`RequireAdmin` 说明。

### 2.3 验收
- [ ] 登录后 `authStore.isAdmin` 正确反映角色；刷新页面后仍保留。
- [ ] 任一接口返回 409 时，调用方能 `catch (e) { if (e.code === 409) ... }` 且不被自动 toast；其余码原有行为不变。
- [ ] `npm run test` 至少有一例绿；`npm run lint` / `npm run build` 通过。

## 4. FE-B —— 管理员改店铺 UI（对应后端 Phase B）

### 4.1 目标
为管理员提供店铺编辑入口；编辑页接乐观锁——并发覆盖时弹"已被他人修改，请刷新"而非静默成功。

### 4.2 后端依赖
后端 **B3（角色鉴权上线）+ B4（`PUT /api/v1/admin/shops/{id}`）+ B5（返回 409）** 必须先就位；`/auth/login`、`/users/me` 须返回 `role`。

### 4.3 开发步骤
- [ ] **F11 API 客户端**：新建 `src/api/admin.ts`——`getAdminShop(id)`、`updateShop(id, req)`（`http.put`，字段对齐 `UpdateShopRequest`）；店铺列表可复用 `shop.ts` 的 `listShops`，或新增 `listAdminShops`（返回含 `status`/`version`）。
- [ ] **F12 管理后台入口**：`src/components/layout/MainLayout.tsx` 顶栏在 `isAdmin` 时显示"管理后台"链接 → `/admin/shops`；非管理员不渲染。
- [ ] **F13 店铺管理列表页**：新建 `src/pages/admin/AdminShopListPage.tsx`——卡片式列出店铺（复用 `ShopCard` 视觉或 admin 专用卡片），每卡带「编辑」「删除」操作。列表态展示 `status`（正常/已下架）。
- [ ] **F14 店铺编辑页**：新建 `src/pages/admin/AdminShopEditPage.tsx`——表单字段：`name` / `category`（下拉取 `GET /shops/categories`）/ `city`（下拉取 `utils/constants.ts` 的 `CITIES`）/ `address` / `phone` / `coverUrl`（复用 `UploadImage` 组件）/ `description`（textarea）。提交走 `updateShop`。
- [ ] **F15 乐观锁冲突 UX**：提交 `catch` 到 `e.code === 409` → AntD `Modal.warning`："该店铺已被其它管理员修改并保存，请先加载最新内容再编辑"，按钮「加载最新内容」→ 重新 `getAdminShop(id)` 回填表单（并把本地未保存改动以 diff 提示）。命中 409 时**不**再 toast（FE-0 已抑制）。
- [ ] **F16 路由与守卫**：`/admin/shops`、`/admin/shops/:id/edit` 套 `RequireAdmin` + `MainLayout`，置于 `RequireAuth` 之后。
- [ ] **F17 校验与防呆**：表单校验沿用 AntD `Form` rules（name 必填、phone 格式等），与后端 `@Valid` 字段一致；`coverUrl` 必须是经 `/files/image` 返回的 URL（沿用 CLAUDE.md 的"先上传拿 URL"约定）。
- [ ] **F18 测试**：`AdminShopEditPage` 用 msw 模拟 200 成功 / 409 冲突两条响应，断言冲突时出现 modal 且表单被回填；`RequireAdmin` 守卫对非管理员重定向。
- [ ] **F19 文档**：`docs/03` 增 `admin` 模块与路由表；`docs/05` 确认 `PUT /api/v1/admin/shops/{id}` 契约（后端负责，前端核对字段）。

### 4.4 视觉系统注意
- admin 页**不要**用 AntD 默认 `Card`/`Table` 橘色主题；卡片用 `tokens.ts` 的 `surface`/`ink`/`rule`，标题用 `Eyebrow`/`SectionTitle`，按钮主色 `appetite`/`ember`。
- 删除按钮用 `appetite` 语义红色，且放在卡片右侧顺位。

### 4.5 风险与回滚
- 风险：admin 列表/编辑回退 AntD 默认样式；409 处理漏写导致用户以为成功。
- 回滚：admin 路由整体下线（移除入口与路由）即可，普通用户路径不受影响。

## 5. FE-C —— 店铺删除 UI（对应后端 Phase C）

> 与 FE-B 共用同一管理后台前端面。删除语义取决于后端选 C-Light（软删）还是 C-Full（物理删+延时清理）——前端各自只差一处"删除后状态"展示。

### 5.1 后端依赖
后端 **`DELETE /api/v1/admin/shops/{id}`** 就位；admin 列表返回 `status`（软删）或物理删后从列表消失。

### 5.2 开发步骤
- [ ] **F21 删除动作**：`AdminShopListPage` 卡片的「删除」按钮。
- [ ] **F22 安全二次确认**：AntD `Modal.confirm`，破坏性操作——文案强提示"删除后不可立刻恢复，关联的点评/评论/点赞将延时清理"；建议**输入店铺名二次确认**（防误删）。确认后调 `deleteShop(id)`。
- [ ] **F23 删除后状态**：
  - **C-Light（软删）**：不立即移除，置卡片为「已下架」灰态徽章（用 `muted`/`rule` token），可保留「恢复」入口（如后端提供恢复端点，留扩展位）。
  - **C-Full（物理删）**：乐观从列表移除，toast "已删除，关联数据将在稍后自动清理"。
- [ ] **F24 错误处理**：删除失败（非 409）走拦截器通用 toast；权限不足（403）提示无操作权限。
- [ ] **F25 文案与一致性**：与 B 的 admin 卡片视觉一致；"清理中/已下架"徽章走 `src/components/editorial/` 风格小标签。
- [ ] **F26 测试**：msw 模拟 softDelete / hardDelete 两条路径，断言列表状态正确变化与二次确认交互。

### 5.3 风险与回滚
- 风险：误删（没做二次确认）、C-Full 下 MQ 清理失败但前端已显示"删除成功"造成预期差。
- 回滚：删除按钮隐藏即可；软删路径在数据层天然可逆。

## 6. FE-D —— ES 搜索前端（对应后端 Phase D）

### 6.1 目标
店铺列表的关键词检索改用 ES 后端能力，前端做体验增强：防抖、命中高亮、延迟文案、空状态。

### 6.2 后端依赖
后端 **D6** 决定接口形态——**优先保持 `GET /api/v1/shops?keyword=` 路径与 `ShopVO` 不变**（前端改动最小）；若后端新增 `GET /api/v1/search`，前端新增对应客户端。

### 6.3 开发步骤
- [ ] **F31 搜索客户端**：如路径不变，复用 `src/api/shop.ts` 的 `listShops`；如新增 `/search`，新建 `src/api/search.ts`。
- [ ] **F32 关键词防抖**：`ShopListPage` 的搜索输入加 300ms 防抖（避免每个字符打后端/ES）；回车立即触发。
- [ ] **F33 命中高亮组件**：新建 `src/components/editorial/Highlight.tsx`——给定 `text` 与 `query`，把命中片段渲染为带 `gold` 下划线/`appetite` 强调的 `<mark>`（样式取自 tokens，禁散落 hex），用于 `ShopCard` 的店名。
- [ ] **F34 空状态与骨架**：
  - 空结果：编辑式「未找到相关餐厅」+ 建议词（如热门分类），复用 `SectionTitle`/`PullQuote` 视觉。
  - 加载中：沿用现有骨架或新增编辑式骨架卡，避免闪烁。
- [ ] **F35 延迟文案**：结果区上方一行 `muted` 小字"搜索结果可能略有延迟"，呼应 ES+Canal 的最终一致性口径。
- [ ] **F36 筛选并存**：城市/分类筛选与关键词组合查询（交后端 bool query）；前端保持 `CITIES`、`/shops/categories` 下拉的现有交互。
- [ ] **F37 分页**：沿用 AntD `Pagination` + `page`/`size`；深分页（`search_after`）留待后端演进，前端暂不改造。
- [ ] **F38 可选：全局搜索框**：`MainLayout` 顶栏加搜索框 → 跳 `/shops?keyword=`（仅在有强需求时做，标记可选）。
- [ ] **F39 测试**：msw 模拟 ES 返回，断言防抖节流、高亮渲染、空状态文案、延迟提示存在。
- [ ] **F40 文档**：`docs/03` 更新搜索交互与 `Highlight` 组件；`docs/05` 核对 `keyword` 行为升级文案（后端负责）。

### 6.4 视觉系统注意
- 高亮色用 `gold`（精选/金标）或 `appetite`（主色），**不**新增颜色；`<mark>` 的背景用 `rule` 系淡色，保持"暖纸"底调。
- 空状态用编辑式排版，不要 AntD 默认 `Empty` 的插画，保持杂志感。

### 6.5 风险与回滚
- 风险：ES 暂时不可用导致搜索报错；命中高亮在前端做需防 XSS（对 query 做转义）。
- 回滚：关键词开关降级——若后端保留了 `LIKE` 降级，前端不需改动；若颜色/高亮出问题，移除高亮组件即可退回纯文本。
