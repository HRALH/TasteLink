## 1. 用户与鉴权模块

### 1.1 注册 *(公开)*
- **功能**:新用户以 用户名 + 密码 注册。
- **接口**:`POST /api/v1/auth/register`
- **写表**:`t_user`(密码 BCrypt `strength=10` 加密存储,`role` 默认 `USER`)
- **约束**:用户名唯一;密码长度 ≥ 8 且含字母 + 数字;用户名已存在 → `40901`。
- **返回**:`{userId, username}`(不含 token,需另行登录)。

### 1.2 登录 *(公开)*
- **功能**:账号密码登录,签发 JWT。
- **接口**:`POST /api/v1/auth/login`
- **写表**:无(纯读校验;成功签发 24h JWT,含 `userId/username/role`)
- **防爆破**:同一用户名 10 分钟内连续失败 5 次 → `42901`(HTTP 200,业务码,前端按普通错误提示);成功自动清零。
- **返回**:`{token, expiresInSec, userId, username, nickname, avatarUrl}`。注意 `role` **不**在返回体里,前端从 JWT claim 解出仅做 UI 提示,真正鉴权在服务端。

### 1.3 登出 *(登录)*
- **功能**:把当前 token 的 `jti` 写入 Redis 黑名单(TTL = token 剩余有效期),命中黑名单的 token 再访问受保护接口返回 401。
- **接口**:`POST /api/v1/auth/logout`
- **降级**:Redis 缺席静默成功,降级为「仅前端清本地态」;过期/非法 token 同样静默成功。前端 best-effort 调用后清本地登录态即可。

### 1.4 查询·我的完整资料 *(登录)*
- **功能**:取当前登录用户完整资料。
- **接口**:`GET /api/v1/users/me`(此规则须在 `GET /users/**` 通配白名单**之前**声明,否则会被通配吃掉)
- **读表**:`t_user`
- **返回**:`UserVO` 本人含全部字段(含 `hasFollowed` 语义不适用于本人)。

### 1.5 修改·我的资料 *(登录)*
- **功能**:改自己的昵称 / 头像 / 简介。仅可改本人,`username` 不可改。
- **接口**:`PUT /api/v1/users/me`(字段均可选,非空才更新)
- **写表**:`t_user`(nickname / avatar_url / bio)

### 1.6 查询·任意用户主页 *(公开)*
- **功能**:看某用户的公开主页资料。
- **接口**:`GET /api/v1/users/{userId}`
- **读表**:`t_user`(展示 id,nickname,avatarUrl,bio,followingCount,followerCount,reviewCount);若登录则附 `hasFollowed`(是否已关注该用户)。

### 1.7 查询·某用户发布的点评 *(公开)*
- **功能**:看某用户发过的点评。
- **接口**:`GET /api/v1/users/{userId}/reviews?page=&size=`
- **读表**:`t_review` + `t_review_image` + `t_user` + `t_shop`(装 VO)
- **返回**:`PageResult<ReviewVO>`

## 2. 店铺浏览与检索模块

> 这是游客消耗最多的「基础查询」模块,4 个查询 + 1 个排序语义都公开。

### 2.1 查询·店铺列表 / 检索 *(公开)*
- **功能**:按 关键词 / 分类 / 城市 筛选店铺,按热度或评分排序并分页。
- **接口**:`GET /api/v1/shops?keyword=&categoryId=&city=&sortBy=&page=&size=`
- **读表**:keyword 命中走 **Elasticsearch**(`name` MUST + status/categoryId/city 过滤 + 0-based 分页)→ 拿有序 id 回查 MySQL 组装 `ShopVO`(回查时再校 `status=normal`);ES 失联/禁用自动降级回 MySQL `LIKE name`;无 keyword 时直读 MySQL `t_shop`。
- **排序**:`sortBy` 默认 `review_count`(热度);keyword 命中 ES 时按 **relevance**,忽略 `sortBy`。
- **中间件**:Redis 不参与;ES 开关 `SEARCH_ENABLED`(默认 `true`),关 / 失败 → 回 `LIKE`,前端无感。
- **infra 待办**:标准 ES 镜像无 IK 中文分词,中文连续命中弱(≈ `LIKE`),装 `analysis-ik` + reindex 后才提升;详见 `docs/08 §5.3`。

### 2.2 查询·店铺详情 *(公开)*
- **功能**:看一家店的全貌:基础信息 + 近期 3 条点评预览。
- **接口**:`GET /api/v1/shops/{shopId}`
- **读表**:`t_shop` + `t_review` + `t_review_image` + `t_user`(装近期点评 VO)
- **返回**:`ShopDetailVO`(继承 `ShopVO`,附 `phone`/`description`/`likeCount`/`topReviews`);不存在 → 404。

### 2.3 查询·店铺下点评流 *(公开)*
- **功能**:一家店下全部点评,按时间或热度排序分页。
- **接口**:`GET /api/v1/shops/{shopId}/reviews?page=&size=&sortBy=`(`sortBy` = `time`(默认) / `like`(热度))
- **读表**:`t_review` + `t_review_image` + `t_user`
- **返回**:`PageResult<ReviewVO>`(登录则附 `hasLiked`)

### 2.4 查询·分类字典 *(公开)*
- **功能**:取店铺分类列表(首页/列表筛选条用)。
- **接口**:`GET /api/v1/shops/categories`
- **读表**:`t_shop_category`
- **返回**:`List<CategoryVO>`(`id, code, name, iconUrl, sortOrder`)

## 3. 点评模块

### 3.1 发布点评 *(登录)*
- **功能**:对某店铺发图文点评(评分 1~5 + 文字 + 最多 9 张图)。
- **接口**:`POST /api/v1/shops/{shopId}/reviews`
- **写表**:`t_review`(主写)+ 同事务维护 `t_shop.review_count / rating_sum / avg_rating`(按店铺 city 冗余写入点评 `city`) + `t_user.review_count`;图片先经 `POST /files/image` 拿到 URL,再随点评提交(`t_review_image`,按 `sort_order` 有序)。
- **返回**:`ReviewVO`(含新生成的 `id`)

### 3.2 查询·点评详情 *(公开)*
- **功能**:看一条点评的完整内容(文字/图/作者/点赞数/评论数)。
- **接口**:`GET /api/v1/reviews/{reviewId}`
- **读表**:`t_review` + `t_review_image` + `t_user`;登录则读 `t_review_like` 判 `hasLiked`。
- **返回**:`ReviewVO`

## 4. 互动模块(点赞 / 评论)

> 全部写操作**幂等**(唯一约束 + 受影响行数双重保证),重复操作视为成功。

### 4.1 点赞点评 *(登录,幂等)*
- **功能**:给一条点评点赞。
- **接口**:`POST /api/v1/reviews/{reviewId}/likes`
- **写表**:`t_review_like`(`uk_review_user` 唯一) ;命中重复 → `DuplicateKeyException` 当成功返回当前计数(不报错);成功后同事务 `review.like_count + 1`、店铺 `like_count + 1`。
- **副作用**:事务提交后 `afterCommit` 写 Redis 热度 ZSet(`like*100 + min(reply,99)`);**重复路径不写**。
- **返回**:`{likeCount}`
- **幂等码**:`40902` 已点赞(HTTP 200,前端拦截器当成功)。

### 4.2 取消点赞 *(登录,幂等)*
- **功能**:撤回点赞。
- **接口**:`DELETE /api/v1/reviews/{reviewId}/likes`
- **写表**:`t_review_like`;`affected rows > 0` 才 `review.like_count - 1`(经 `GREATEST(0, n-1)` 防负);未点过也返回成功,计数不变。
- **副作用**:`afterCommit` 从热度 ZSet `zrem`(撤赞降低热度)。
- **返回**:`{likeCount}`

### 4.3 查询·点评评论列表 *(公开)*
- **功能**:看一条点评下的评论(单层,无楼中楼)。
- **接口**:`GET /api/v1/reviews/{reviewId}/comments?page=&size=`
- **读表**:`t_review_comment` + `t_user`
- **返回**:`PageResult<CommentVO>`

### 4.4 发表评论 *(登录)*
- **功能**:对一条点评发评论。
- **接口**:`POST /api/v1/reviews/{reviewId}/comments`
- **写表**:`t_review_comment`(主写)+ 同事务 `review.reply_count + 1`。
- **副作用**:评论成功后给点评作者发「被评论」通知(见 §5.x / §6)。
- **返回**:`CommentVO`(含生成 `id`)

## 5. 关注模块

### 5.1 关注用户 *(登录,幂等)*
- **功能**:关注别人。
- **接口**:`POST /api/v1/users/{userId}/follow`
- **约束**:不可关注自己 → `40904`;已关注 → `40903`(HTTP 200,当成功)。
- **写表**:`t_follow`(`uk_follower_followee` 唯一);成功后同事务双方 `following_count` / `follower_count + 1`。
- **副作用**:成功后给被关注者发「被关注」通知。
- **返回**:`{followingCount}`

### 5.2 取消关注 *(登录,幂等)*
- **功能**:取关。
- **接口**:`DELETE /api/v1/users/{userId}/follow`
- **写表**:`t_follow`;`affected rows > 0` 才双方计数 - 1(`GREATEST 0` 防负)。
- **返回**:`{followingCount}`

### 5.3 查询·关注列表 *(公开)*
- **功能**:看某人关注了谁。
- **接口**:`GET /api/v1/users/{userId}/followings?page=&size=`
- **读表**:`t_follow` + `t_user`
- **返回**:`PageResult<UserVO>`(被关注者摘要)

### 5.4 查询·粉丝列表 *(公开)*
- **功能**:看某人的粉丝。
- **接口**:`GET /api/v1/users/{userId}/followers?page=&size=`
- **读表**:`t_follow` + `t_user`
- **返回**:`PageResult<UserVO>`

### 5.5 查询·关注 feed「关注的人的点评」 *(登录)*
- **功能**:看自己关注的人最近发了哪些点评(拉取式 feed)。
- **接口**:`GET /api/v1/feed/following?page=&size=`
- **读表**:取 `t_follow`(我关注谁) → `t_review`(这些人的点评按 `create_time` 倒序分页) → 复用 `assemble` 装 VO。无关注对象返回**空分页**(非报错)。
- **性能**:无 keyword、纯时间线;`IN(followeeIds) + ORDER BY create_time` 会 filesort,MVP 数据量可接受,后期可加 `idx_status_create` 优化。

## 6. 首页模块

### 6.1 查询·首页热门内容 *(公开)*
- **功能**:首页一次性给「热门店铺 + 热门点评」各 10 条,可按城市过滤。
- **接口**:`GET /api/v1/home?city=`
- **读表**:
  - 热门店铺:`t_shop` `WHERE city=? AND status=1 ORDER BY review_count DESC, like_count DESC LIMIT 10`(无 city 全局)。
  - 热门点评:**无城市过滤时**优先读 Redis 热度 ZSet(`HotRankService.topReviewIds`,`ZREVRANGE` 取 id 批量加载并按缓存序重排);有城市过滤或缓存不可用 → 回 MySQL(`like_count DESC, reply_count DESC`)。
- **中间件**:Redis 开关 `RANK_CACHE_ENABLED`(默认 `true`),关 / 失败 → 纯 MySQL;`ScheduledRankRebuild` 定时对账修复缓存漂移。**Phase A 只缓存全局热门**,带 city 的首页始终走 MySQL。
- **返回**:`HomeVO = {hotShops: ShopVO[], hotReviews: ReviewVO[]}`

## 7. 通知模块(产品优化 F1)

> 通知在被赞 / 被评 / 被关注瞬间写入(自己给自己的操作不发——`actor==user` 跳过;关注另有「不可关注自己」前置)。**关系式而非快照**:`actor_id` 关联,读时批量回查 `t_user` 取昵称头像,避免改昵称后通知文案过期。
> 通知与核心互动**同事务原子提交**(非 `afterCommit`,因同库不算外部 IO),`NotificationService.create` 内部吞一切异常 log.warn,绝不阻塞核心写。

| 触发点 | 通知类型 | 接收者 |
|---|---|---|
| `like()` 真实新赞后 | `REVIEW_LIKED` | 点评作者 |
| `createComment()` 真实新评论后 | `REVIEW_COMMENTED` | 点评作者(preview = 评论内容片段) |
| `follow()` 真实新关注后 | `USER_FOLLOWED` | 被关注者 |

### 7.1 查询·我的通知列表 *(登录)*
- **功能**:看我收到的通知(时间倒序)。
- **接口**:`GET /api/v1/notifications?page=&size=`
- **读表**:`t_notification` + 批量回查 `t_user`(取 actor 昵称头像)
- **返回**:`PageResult<NotificationVO>`

### 7.2 查询·未读数 *(登录)*
- **功能**:数未读通知条数(驱动顶栏红点)。
- **接口**:`GET /api/v1/notifications/unread-count`
- **读表**:`t_notification`(`selectCount where user_id=? and is_read=0`)
- **返回**:`{count}`
- **前端**:顶栏铃铛 `react-query refetchInterval: 30000`(30s 轮询,仅登录态启用,全站首个轮询用例)。

### 7.3 标记单条已读 *(登录,幂等)*
- **功能**:`POST /api/v1/notifications/{id}/read`(`is_read=1`,不存在/已读都算成功)。

### 7.4 全部已读 *(登录)*
- **功能**:`POST /api/v1/notifications/read-all`(`is_read=1 where user_id=? and is_read=0`)。

## 8. 文件上传模块

### 8.1 上传图片 *(登录)*
- **功能**:上传一张图,拿回可直接 `<img src>` 的 URL(发点评前先调)。
- **接口**:`POST /api/v1/files/image`(`multipart/form-data`,字段 `file`)
- **写表**:无关系表写入;文件落 `storage.type` 决定 ——`local` 写 `./data/uploads/yyyy/MM/uuid.ext` 经 `/static/uploads/**` 暴露;`oss` 写阿里云 OSS。
- **约束**:校验类型(jpg/png/webp 等)与大小;文件名 UUID 化。
- **返回**:`{url, ossKey}`(业务代码只依赖 `FileStorageService` 接口,从不自己拼 URL)。

## 9. 管理员后台模块

> 路径前缀 `/api/v1/admin/**`,`SecurityConfig` 强制 `hasRole('ADMIN')`;普通用户 403,未登录 401。`role` 随登录写入 JWT claim。种子 `admin` 账号是**占位哈希不可登录**,提权真实管理员:注册一个号 → `UPDATE t_user SET role='ADMIN' WHERE id=?`。

### 9.1 编辑店铺 *(管理员,乐观锁)*
- **功能**:改店铺资料(字段非空才更新)。
- **接口**:`PUT /api/v1/admin/shops/{shopId}`
- **写表**:`t_shop`(`version` 乐观锁:`selectById` 载入版本 → 覆盖非空字段 → `updateById` 自动 `WHERE id=? AND version=?` + `SET version+1`);冲突 → 影响行数 0(MyBatis-Plus **不抛** `OptimisticLockingFailureException`,需服务层把 `affected==0` 映射为 `BusinessException(SHOP_VERSION_CONFLICT)`,HTTP **409**)。
- **返回**:`ShopDetailVO`;不存在 → 404;`categoryId` 非空时校验分类存在性(不存在 400)。
- **前端**:409 走 `request.ts` 的 `PROCESSABLE_CODES`,抛 `ApiError(code)` 不自动 toast,前端弹「加载最新内容」让管理员重拉。

### 9.2 删除店铺 *(管理员,延时清理)*
- **功能**:删店走两段式 —— 标记阶段同事务 `shop.status=0` + 级联 `review.status=0`(即时从所有公开读路径消失,含首页热门,后者过滤 `status=normal`)+ 镜像回扣发布用户 `review_count`;事务提交后 `afterCommit` 发 RabbitMQ 延时消息(默认 5s 延时窗口便于「撤销误删」),到期消费者级联**物理删** `t_review_image → t_review_like → t_review_comment → t_review → t_shop` + 删 OSS/本地图 + 从热度 ZSet `zrem`。
- **接口**:`DELETE /api/v1/admin/shops/{shopId}`
- **可靠性**:TTL+DLX 免插件延时投递;毒消息走 DLQ(`retry` + `default-requeue-rejected=false` + 队列 `x-dead-letter-exchange`);无单独 outbox 表,`ScheduledShopCleanupReconcile` `@Scheduled` 扫 `status=0` 且过 `delay+grace` 的店直接重跑清理(幂等)作 at-least-once 兜底。
- **降级**:`RABBIT_ENABLED=false` 仍能删店(标记+隐藏+回扣立即生效),物理清理改由对账调度直接做(无延时窗口)。
- **并发**:改/删冲突仍 409;二次删除返回 404(幂等口风)。

### 9.3 查询·后台点评列表(含已下架) *(管理员)*
- **功能**:内容治理列表,可按状态筛(正常/已下架/全部)。
- **接口**:`GET /api/v1/admin/reviews?page=&size=&status=`(status 1 正常/0 已下架,省略=全部)
- **读表**:`t_review` + 批量回查 `t_shop`(店名)+ `t_user`(昵称)
- **返回**:`PageResult<AdminReviewVO>`(附 `status` 区分)

### 9.4 下架点评 *(管理员,产品优化 F4)*
- **功能**:`PUT /api/v1/admin/reviews/{id}/hide` —— 置 `review.status=0`,同事务镜像回扣 `t_shop.review_count / rating_sum`(`GREATEST 0` 防负)、重算 `avg_rating`、递减 `t_user.review_count`,`afterCommit` 从热度 ZSet `zrem`。**不物理删,可恢复**。

### 9.5 恢复点评 *(管理员)*
- **功能**:`PUT /api/v1/admin/reviews/{id}/restore` —— 反向 +1、重算 avg。
- **约束**:点评不存在或未下架 → 404;**店铺已下架 → 404**(防止给已下架店铺恢复点评导致计数虚增)。

### 9.6 查询·后台举报记录 *(管理员)*
- **功能**:运营查举报线索(moderation 决策 UI 为后续工作流,本次仅展示)。
- **接口**:`GET /api/v1/admin/reports?page=&size=&status=`(`PENDING`/`RESOLVED`,省略=全部)
- **读表**:`t_report` + 批量回查 `t_user`(举报人昵称)
- **返回**:`PageResult<ReportVO>`

## 10. 内容治理模块(产品优化 F4)—— 用户侧入口

### 10.1 提交举报 *(登录,幂等)*
- **功能**:用户举报一条点评(对外前最低安全网)。
- **接口**:`POST /api/v1/reports`
- **写表**:`t_report`(`uk_reporter_target` 唯一,同一人对同一目标只记一条)
- **约束**:`targetType` ∈ `{REVIEW, COMMENT, USER, SHOP}`(非法 → 400);`reason` ≤ 255;`targetId` 必填。
- **幂等**:重复举报 → 唯一键冲突 → `40905`「已举报过该内容」(HTTP 200,前端默认错误路径 toast 友好提示,无需特殊分支)。
- **前端入口**:`ReviewCard` 操作区(点评非作者、登录后)出现「举报」按钮 → `Modal` + `Select` 选理由 → 提交。

## 11. 中间件降级与待办一览

三项中间件(V2)均「应用层完成、infra 待办」,带特性开关,缺位时各自降级回 MySQL,应用照常启动:

| 中间件 | 关联功能 | 开关(默认 `true`) | 关 / 失败后降级行为 | infra 待办 |
|---|---|---|---|---|
| Redis | 首页热门点评排行(§6.1) | `RANK_CACHE_ENABLED` | 读回 MySQL(`like_count, reply_count` 排序);`ScheduledRankRebuild` 兜底对账 | — |
| RabbitMQ | 删店延时清理(§9.2) | `RABBIT_ENABLED` | 不发消息,对账调度直接物理清理(删店仍生效,无延时窗口) | — |
| Elasticsearch | 店铺关键词检索(§2.1) | `SEARCH_ENABLED` | keyword 回 MySQL `LIKE name` | 装 `analysis-ik` + reindex 提升中文命中;部署 Canal binlog 增量同步(当前靠 `ScheduledShopReconcile` 定时全量重建) |
| XXL-JOB(B5) | 三个对账任务的触发(§6.1 / §9.2 / §2.1) | `XXL_JOB_ENABLED`(默认 **`false`**) | 关 → 仍走本地 `@Scheduled` + ShedLock(即未接入前的行为);**失败** → 无降级,对账任务静默停摆(唯一高风险点,见 `docs/08 §5.4`) | — |

> 延后(本次不做):敏感词过滤、审核工作流、Canal、IK、LBS、Redisson —— 见 `docs/11` 延后项(`XXL-JOB` 已于 B5 落地)。
