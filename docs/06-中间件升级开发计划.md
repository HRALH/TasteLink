## 0. 背景与目标

在 MVP（单库 MySQL、无缓存/MQ/ES）跑通之后，规划引入四项中间件能力以支撑后续版本：

| 编号 | 能力 | 选型 |
|---|---|---|
| F1 | 点评审热度排行缓存 | Redis SortedSet + 定时对账（先 `@Scheduled`，后视情况上 XXL-JOB） |
| F2 | 管理员并发改店铺防覆盖 | 角色鉴权 + MyBatis-Plus 乐观锁（先 `@Version`，多实例再上 Redisson） |
| F3 | 店铺删除后延时清理关联评论/点赞 | RabbitMQ 延时队列（先逻辑删轻量支，物理删走完整支） |
| F4 | 美食关键词检索 | Elasticsearch + Canal 增量同步 |

> **前提说明**：这四项原本都在 `docs/01 §6.2`「MVP 明确不做」清单内。本计划即把相关条目转正升级，故**务必同步更新 `docs/01`/`02`/`04`/`05` 与 `CLAUDE.md`**，避免代码与 spec 永久错位。

### 0.1 总体原则（贯穿全阶段）

1. **先轻量变体、后重变体**：每项先用最简实现跑通，把运维重变体（XXL-JOB / Redisson / 物理删级联留）留到最后按需升级。
2. **先补产品面、再叠中间件**：F2/F3 依赖 MVP 缺失的角色鉴权与店铺写/删端点，必须先把这些产品面铺出来，否则中间件悬空。
3. **每步独立可验收、可回滚**：每阶段配一个特性开关（`tastelink.xxx.enabled`），出问题降级回 MySQL 主路径。
4. **先有测试再上中间件**：当前 `backend/src/test` 为空，引入中间件前必须先补该阶段集成测试，否则 Redis/MQ/ES 行为无法验证。

> 注：v2 实施后 `backend/src/test` 已建立单元测试 + Testcontainers 集成测试基线（`HotRankServiceIT` / `AdminShopServiceIT` / `ShopCleanupIT` / `SearchServiceIT`，均 `@SpringBootTest` + 真中间件，`-DRUN_IT=true` 触发）。

## 1. 总体顺序与依赖

由易到难：**Phase A（F1）→ Phase B（F2）→ Phase C（F3）→ Phase D（F4）**。

```
Phase A  引入 Redis ──────────────┐（Redis 被 B 的 Redisson 变体复用）
Phase B  引入角色鉴权（shop 写）─┐（角色鉴权被 C 的店铺删除复用）
Phase C  引入 RabbitMQ ─────────┐
Phase D  引入 ES + Canal ───────┘（最重，最后做；缺失风险最高）
```

- **A 最易**：排行查询与点赞写路径已存在，纯加法、可灰度、纯后端、可回滚；顺手把 Redis 引入供 B 复用。
- **B 中**：一次性改全局安全模型（二态→`hasRole`），是 C 的解锁器；锁本身用乐观锁即可，不增中间件。
- **C 中高**：新增消息中间件 + 可靠投递/幂等/对账；且依赖"店铺删除"产品决策。若选逻辑删，**重支可整体跳过**。
- **D 最重**：两个新中间件 + binlog/Canal 账号 + 索引 mapping 演进 + 改写公共读路径 + 最终一致性面。

## 3. Phase A —— F1 点评审热度排行（Redis ZSet + `@Scheduled`）

### 3.1 目标
首页「热门点评」从 `ORDER BY like_count DESC, reply_count DESC LIMIT 10`（MySQL filesort）改为 Redis ZSet 的 `ZREVRANGE`，O(log N)；旁挂定时对账修复 ZSet 与 MySQL 计数漂移。

### 3.2 关键设计
- **Key 设计**：`review:hot`（全局）；按城市时 `review:hot:{city}`。成员 = `reviewId`，score = `likeCount * 100 + min(reply_count, 99)`（以单 score 兼容「先点赞数后评论数」的二级排序口径）。
- **一致性口径**：点赞写 MySQL `like_count` 仍在 `@Transactional` 内；ZSet 写在**事务提交后**（`TransactionSynchronization#afterCommit`），保证 DB 回滚则 ZSet 不增。即便偶发漂移，定时对账兜底。
- **读路径**：`home` 热门点评先 `ZREVRANGE` 取 reviewId，再批量 `selectBatchIds` 补全 `ReviewVO`（避免 N+1，复用现有 `batchUsers` 思路）。**ZSet 为空或异常 → 降级回 MySQL 排序**。

### 3.3 开发步骤
- [ ] **A1 引依赖**：`pom.xml` 加 `spring-boot-starter-data-redis`（Lettuce 自动装配）。
- [ ] **A2 RedisConfig**：新建 `config/RedisConfig.java`，暴露 `StringRedisTemplate`（ZSet 成员/分数均为字符串/数字，避免 JDK 序列化器坑）。
- [ ] **A3 HotRankService**：新建 `service/HotRankService` + `impl/HotRankServiceImpl`，方法：`increment(reviewId, city)`、`decrement(reviewId, city)`、`topN(city, n)`、`rebuild(city)`。开关 `tastelink.rank.cache-enabled`。
- [ ] **A4 接入点赞路径**：`InteractionServiceImpl.like/unlike` 中，DB 计数更新保持原状；新增 afterCommit 钩子调用 `hotRankService.increment/decrement`。
- [ ] **A5 替换读路径**：`RecommendServiceImpl` 热门点评改为先查 ZSet、批量回填 VO；空则走原 SQL。`HomeController` 返回结构不变（前端零改动，纯后端阶段）。
- [ ] **A6 定时对账**：新建 `config/ScheduledRankRebuild`，`@Scheduled(cron="0 */10 * * * *")` 全量 `review_like_count` 回写 ZSet，修复漂移与冷启动空 ZSet。
- [ ] **A7 集成测试**：`HotRankServiceIT`（Testcontainers Redis）覆盖：点赞后排名上升、取消后下降、对账后与 MySQL 一致、ZSet 故障降级 MySQL。
- [ ] **A8 配置与文档**：`application*.yml` 补 redis 占位；`docs/02` 技术栈加 Redis + 调度；`CLAUDE.md` 配置表加 `REDIS_*`。

### 3.4 风险与回滚
- 风险：Redis 不可用 / ZSet 漂移 / 冷启动空排行。
- 回滚：`tastelink.rank.cache-enabled=false` 直接退回 MySQL 排序，前端无感。

## 4. Phase B —— F2 管理员并发改店铺（角色鉴权 + 乐观锁）

> 本阶段一次性付清「角色鉴权」架构成本，被 Phase C 的店铺写/删复用。锁默认走**乐观锁**；Redisson 仅作 4.5 延后变体。

### 4.1 目标
引入管理员身份并把店铺编辑接入并发控制：两人同时改同一店铺时，后提交者得到「内容已被他人修改，请刷新」而非静默覆盖。

### 4.2 关键设计
- **角色落地**：`t_user` 增 `role VARCHAR(16) NOT NULL DEFAULT 'USER'`（取值 `USER`/`ADMIN`）；种子一个 ADMIN 账号（`data.sql`）。JWT claims 内带 `role`，`LoginUser` 增 `role` 属性。
- **鉴权升级**：`SecurityConfig` 由「permitAll/authenticated 二态」升级，新增 `/api/v1/admin/**` → `hasRole('ADMIN')`；保持既有白名单顺序敏感规则不动。
- **乐观锁**：`t_shop` 增 `version INT NOT NULL DEFAULT 0`；实体 `@Version private Integer version`；`MybatisPlusConfig` 的 `MybatisPlusInterceptor` 链上 `OptimisticLockerInnerInterceptor`。`updateById` 冲突时受影响行=0 → 抛 `BusinessException(SHOP_VERSION_CONFLICT)`。

### 4.3 开发步骤
- [ ] **B1 DDL**：`schema.sql`/`data.sql` + `docs/04 §3.1/§3.3` 加 `role`、`version` 列与 ADMIM 种子。
- [ ] **B2 实体与拦截器**：`User` 加 `role`；`Shop` 加 `@Version version`；`MybatisPlusConfig` 链入 `OptimisticLockerInnerInterceptor`。
- [ ] **B3 安全链**：`JwtUtil` 签发带 `role` claim；`JwtAuthFilter` 解析写入 `LoginUser`；`SecurityConfig` 增 `/api/v1/admin/**` 规则（置于 `anyRequest().authenticated()` 之前）。
- [ ] **B4 管理员写端点**：新建 `controller/AdminShopController`（`/api/v1/admin/shops`），`PUT /{id}` 编辑；new `dto/request/UpdateShopRequest`（带校验）；new `service/AdminShopService` + impl。
- [ ] **B5 冲突处理**：`AdminShopServiceImpl.updateShop` 用 `selectById` → 覆盖可改字段 → `updateById`；捕获 `OptimisticLockingFailureException`，抛 `BusinessException(ResultCode.SHOP_VERSION_CONFLICT)`（`ResultCode` 增 `SHOP_VERSION_CONFLICT(409,409,"店铺已被他人修改，请刷新重试")`）。
- [ ] **B6 全局异常**：`GlobalExceptionHandler` 确认对新异常码以 409 返回 `R`，不泄露堆栈。
- [ ] **B7 集成测试**：`AdminShopServiceIT` 双线程并发改同店 → 一成功、一收 409；单改成功后 `version` 自增。
- [ ] **B8 契约与文档**：`docs/05` 新增 `PUT /api/v1/admin/shops/{id}` 与 409 语义；`docs/02` 新增管理员模块与角色鉴权小节；`docs/01 §2.2` 角色边界更新。
- [ ] **B9 前端（可选）**：若需可视管理页，新增 `frontend/src/pages/admin/ShopEditPage`；否则前端零改动、用 Postman 验收。

### 4.4 风险与回滚
- 风险：上 `@Version` 后未捕获冲突会 500（影响写库）—— **必须先上线 B5/B6 再发布写端点**。
- 回滚：乐观锁是增量；若需彻底回滚，移除 admin 端点即可，普通读路径不受影响。

### 4.5 延后变体 B2 —— Redisson 分布式锁（按需）
- 触发条件：后台确为**多实例高并发**、或需跨资源串行化。
- 步骤：`pom` 加 `redisson-spring-boot-starter`；`config/RedissonConfig`; `service/LockService` 用 `RLock`（`tryLock(waitTime, leaseTime, unit)`）；admin 更新包裹锁，拿不到锁→409。
- 复用 Phase A 的 Redis 实例。**单实例后台上 = over-engineering，默认不做。**

## 5. Phase C —— F3 店铺删除延时清理（RabbitMQ 延时队列）

> **关键决策点（必先定）**：店铺删除走「逻辑删」还是「物理删」？
> - **逻辑删**：`status=0` + 关联 reviews/comments 同事务置 0（查询已按 `status=1` 过滤）→ **不需要 MQ，走 C-Light 即可**。
> - **物理删**：才需延时清理关联数据 → 走 **C-Full**。
> MVP 规模下推荐 **C-Light**；C-Full 仅在"删店铺负载明显变重、需空间回收"时再做。

### 5.1 C-Light（推荐：逻辑删，无中间件）
- [ ] **CL1 端点**：`AdminShopController` 增 `DELETE /api/v1/admin/shops/{id}`；`AdminShopService.softDeleteShop` 在**单 `@Transactional`** 内把 `t_shop.status=0` 并级联把该店 `t_review.status=0`、（可选）`t_review_comment.status=0`。
- [ ] **CL2 计数处理**：店铺下架时按需回扣 `t_user.review_count`、`t_shop.avg_rating`，沿用 `GREATEST(0, n-1)` 防负的现有模式。
- [ ] **CL3 契约**：`docs/05` 增 `DELETE` 端点；`docs/04` 说明软删口径。
- [ ] **CL4 测试**：`AdminShopServiceIT` 校验软删后该店点评对公开接口不可见、计数一致。

### 5.2 C-Full（物理删 + RabbitMQ 延时清理）
落地仅当确定物理回收。

#### 5.2.1 关键设计
- **延时方式**：RabbitMQ `rabbitmq_delayed_message_exchange` 插件（推荐，语义直观）；备选 TTL + DLX（免插件、链路多一跳）。
- **消息模型**：`ShopCleanupMessage{shopId, type, sentAt, retry}`；延迟 N（如 5s~60s）便于"撤销误删"窗口。
- **消费动作**：按外→内删除 `t_review_image` → `t_review_like` → `t_review_comment` → `t_review` → `t_shop`；回扣用户计数；调 `FileStorageService.delete(oss_key)` 清图片。
- **可靠性三件套**：publisher confirm + 消费幂等（DELETE 天然幂等 + 业务态防重）+ 死信队列（DLQ）兜底毒消息；必要时加本地 outbox 表保证至少一次投递。

#### 5.2.2 开发步骤
- [ ] **CF1 中间件**：`docker-compose.yml` 加 `rabbitmq`（装延时插件）；`pom.xml` 加 `spring-boot-starter-amqp`。
- [ ] **CF2 RabbitMQConfig**：`config/RabbitMQConfig.java` 定义 `x-delayed-message` 交换器、清理队列、绑定、Jackson 消息转换器、confirm 回调、DLQ 绑定。
- [ ] **CF3 消息与生产者**：`dto/mq/ShopCleanupMessage`；`ShopCleanupProducer.send(shopId, delayMs)`；在 `AdminShopService.deleteShop` 内先逻辑置位/标记，再发延时消息（发消息与置位同事务，建议 outbox）。
- [ ] **CF4 消费者**：`ShopCleanupConsumer @RabbitListener` 执行级联清理；失败重试 + 进 DLQ；幂等校验（shopId 已清则跳过）。
- [ ] **CF5 图片清理**：复用 `FileStorageService.delete(ossKey)` 删 OSS 对象（注意 OSS 失败不阻断主流程，记 DLQ 重试）。
- [ ] **CF6 集成测试**：`ShopCleanupIT`（Testcontainers RabbitMQ）覆盖：删店→延时后关联清空、重复消息幂等、生产失败/消费失败进 DLQ、图片删除。
- [ ] **CF7 文档**：`docs/05` 端点；`docs/02` 加 MQ 架构小节（含可靠性/幂等/DLQ）。

#### 5.2.3 风险与回滚
- 风险：消息丢失导致孤儿评论/图片；幂等不足导致重复清理；OSS 删除失败残留。
- 回滚：C-Full 仅关物理删路径；保留 C-Light 逻辑删作兜底，可随时降级（删操作改为置位、不再发消息）。

## 6. Phase D —— F4 ES + Canal 美食关键词检索（最重，最后做）

### 6.1 目标
店铺/点评搜索由 `name LIKE '%kw%'` 升级为 ES 中文分词检索；Canal 监听 binlog 增量同步，避免应用层双写。

### 6.2 关键设计
- **索引**：先单建 `shop` 索引（字段 `id, name(ik_max_word), category_name, city, address, description, avgRating, reviewCount`，`status=1` 过滤）；review 内容检索按需后置第二期。
- **同步选型**：推荐 **Canal-Adapter 独立部署**（自带 ES adapter，配置化同步，最小代码）；备选在应用内嵌 `canal-client` 自写消费。本计划默认走 Adapter。
- **一致性**：Canal 秒级最终一致；**搜索结果回查 MySQL 详情**（`GET /shops/{id}` 仍 MySQL）兜底短时不一致。
- **读路径**：`GET /shops?keyword=` 改走 ES；分类/城市筛选可并入 bool query，也可暂留 MySQL。分页用 `from/size`（MVP 规模够；深分页留 `search_after` 演进）。

### 6.3 开发步骤
- [ ] **D1 中间件与运维**：`docker-compose.yml` 加 `elasticsearch`（装 IK 分词器）+ `canal-server`；MySQL 开 **binlog row 格式**、建 `canal` 账号；准备 `canal-adapter` 部署配置。 **（infra 待办：ES 已加；IK 未装、canal 未部署、binlog 未开，以 `ScheduledShopReconcile` 定时全量重建兜底）**

- [ ] **D3 引依赖**：`pom.xml` 加 `spring-boot-starter-data-elasticsearch`（SB 3.2 配 `ElasticsearchClient`）。
- [ ] **D4 ESConfig**：`config/ESConfig.java` 暴露 `ElasticsearchClient`；连 ES。
- [ ] **D5 SearchService**：`service/SearchService` + impl，封装 keyword 检索 bool query、分页、`status=1` 过滤、回填 `ShopVO`。

### 6.4 风险与回滚
- 风险：Canal 停摆致搜索陈旧；IK 分词口径不符预期；mapping 变更需 reindex；改写公共读路径出问题用户立可知。
- 回滚：`keyword` 分支降级回 `LIKE`（保留旧 SQL 代码路径，开关控制）；canal-adapter 关停不影响主库写入。
